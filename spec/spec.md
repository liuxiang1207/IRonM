## [2026-10-20]

**当日变更概览**: 新增业务模块依赖方向约束：模块按层次只能向下依赖；安全规则模块不依赖任何其他业务模块；违反时项目的标准检查失败。新增工程基础：统一且可替换的时间来源、可复现的标识生成、环境变量配置、不含健康数据原文的结构化日志。新增数据契约（上）：统一的记录结构与首批记录类型、显式的"未知"缺失值、带精度与可信范围的指标结果，契约可导出为 JSON Schema；澄清可选测量项省略即为"未知（没记录）"；新增"围度"记录类型。新增数据契约（下）：Agent 角色与输出类型、计划字段唯一归属（越权即拒绝）、带调整三件套的提案、只读快照、计划版本、模型调用记录。新增数据存储：本地数据库、按编号的迁移、只追加的记录仓储与中文全文检索。新增规则表：可读的规则文件、启动时严格校验、按编号取规则与参数，首个规则集为数据质量。新增测试骨架：红旗正反例、对抗题库、数据驱动的黄金用例，未实现的功能标预期失败。新增模型选型评测：50 道题、可配置的模型列表、自动初筛判分与对比表；评测支持多币种价格、截断判失败与按账户限额限速。新增快进模拟：5 类模拟用户、隐藏真值与陷阱、按天生成 8 周记录并写入记录仓储。独立审查后补充多项澄清：彻底只读、日志取值受限、拒绝覆盖与未来时间、独立连接、严格的文件与数值格式、陷阱校验，并收紧数据存储的可用范围。新增记录提交接口：校验、幂等去重、冲突识别、不回显内容的错误、每请求独立连接、启动时自动迁移。新增批量与离线补交：逐条独立处理与返回、同批内更正排在原记录之后、提交顺序不影响最终结果。新增异常值“待确认”判定：阈值取自规则表、按数据流逐次比较、更正即确认。

### 1. 工程约束：模块依赖方向

**需求**: 业务模块按层次组织（从上到下大致为：对外接口 → 编排与审查 → 各专业 Agent → Skill → 计算 / 指标 / 安全规则 → 共享契约与基础设施），只允许上层依赖下层，禁止下层反向依赖上层。
**需求**: 安全规则模块（急症拦截、人群分层等）除共享契约与基础设施外，不得依赖任何其他业务模块，保证在离线或模型不可用时仍能独立运行。
**需求**: 数据存储只能被编排、审查和对外接口这几层直接使用；Agent、Skill 和计算层不得直接读写存储，只能使用上层传入的数据。
**需求**: 任何违反上述规则的依赖都使项目的标准检查失败（本地提交前检查与持续集成两处一致），失败信息指明违规的调用方与被调用方。
**约束**: 每个业务模块都必须在分层规则中有明确位置；新增模块未登记分层时同样检查失败，避免绕过约束。
**非目标**: 不限制对第三方库的依赖；不检查测试代码的依赖方向。

**澄清**（独立审查后收紧）: 数据存储只能被编排层与对外接口直接使用；调度、记忆等模块需要持久化时，通过契约中定义的数据访问接口，由上层注入实现。

### 2. 工程基础：时间、标识、配置与日志

**需求**: 系统内所有"当前时间"都取自同一个可替换的时间来源；测试与快进模拟可以把时间固定在某一时刻，或向前拨动。
**约束**: 时间一律带时区，统一按 UTC 表示与比较；不带时区的时间在进入系统时被拒绝（报错，不做猜测）。

**需求**: 服务端生成的标识全局唯一；测试与模拟可指定种子，使同一流程两次运行得到完全相同的标识序列。

**需求**: 运行配置通过 `IRONM_` 前缀的环境变量提供，当前配置项：`IRONM_ENV`（`dev` / `test` / `prod`，默认 `dev`）、`IRONM_LOG_LEVEL`（`debug` / `info` / `warning` / `error`，默认 `info`）。
**约束**: 出现未知的 `IRONM_` 变量或取值非法时，启动直接失败，错误信息指明是哪个变量；不静默忽略、不回退到默认值。

**需求**: 日志为结构化格式，每行一条记录，包含时间、级别、来源、事件名和附加字段；日志时间取自上述同一时间来源。
**约束**: 日志不得包含健康数据原文：事件名必须是固定的标识性名称而非自由文本；附加字段只允许标识类（各种 ID）和运行类信息（状态、耗时、计数、错误类型等），写入其他字段时直接报错；记录异常时只记异常类型，不记异常消息内容。

**需求**: 在固定时间和固定种子下，同一流程两次运行产生的标识与日志逐字一致。
**非目标**: 用户本地时区换算（随记录与复盘功能定义）；日志中对数据内容做哈希（首次需要时再定方案）；日志落盘与轮转。

**澄清**（独立审查后补充）: 日志附加字段的取值也受限：标识类与状态类取值只能是不含空格与中文的短标识，路径不得带查询参数；不经结构化接口、直接写入的日志只输出"拒绝了一条不合规日志"及其来源，不输出其内容。配置项名必须全大写，大小写不同的同名配置视为未知配置而失败。
**澄清**（复核后补充）: 取值格式校验只能挡住含中文、空格、查询参数的文字，挡不住英文单词（如 `chest_pain`）；标识类字段只应传入系统生成的标识，这一点靠代码审阅保证。

### 3. 数据契约：记录、缺失值与指标结果

**需求**: 所有记录使用统一结构：记录标识（由客户端生成，用于去重）、用户、记录类型、发生时间、记录时间、来源（用户 / 设备 / 估算）、是否已确认、原文（用户原话或设备原始字段，可空）、规整后的内容；可选附带客户端提示的精度等级。
**需求**: 首批记录类型：训练打卡、按组记录、称重、每周签到、饮食、身体不适、基线测试。每种类型的规整内容字段固定，单位统一（千克、千卡、克）；内容与类型不匹配时拒绝。
**需求**: 记录只追加不修改；改错是追加一条同类型的更正记录，指向被更正的记录。
**约束**: 发生时间不得晚于记录时间；时间必须带时区；来源为设备时必须注明数据流（不同设备的数据不混算）；数值超出物理上可能的范围时拒绝（如体重不在 20–400 千克）；出现未定义的字段、非有限数字（NaN、无穷）或以文本形式给出的数字时拒绝。这些都在入口直接报错，不做纠正或猜测。

**需求**: 缺失值必须显式标为"未知"并注明原因（没记录 / 不愿提供 / 无法解析 / 数据不足），禁止用 0 或空值代替。
**约束**: "未知"不能参与算术运算，也不能当真假值判断，误用时直接报错。

**需求**: 指标结果包含：指标名、所属领域（训练 / 体重与体成分 / 饮食 / 恢复）、数值或"未知"、单位、可信范围（下限、上限、置信水平）、精度等级（P0–P3）、使用的记录条数、窗口天数、状态（正常 / 数据不足 / 已过期 / 待确认）、还差什么、最近一条记录的时间、计算时间、所用公式编号。
**约束**: 字段之间必须一致，否则拒绝：状态为正常时必须有数值；数值为"未知"时不得有可信范围，状态也不能是正常；可信范围的下限不大于上限且包含数值；状态为数据不足时必须说明还差什么。

**需求**: 全部契约可导出为 JSON Schema 文件并纳入版本库；契约改动后未重新导出时，标准检查失败。
**非目标**: 快照、Agent 输出、计划版本、字段归属、模型调用记录（下一步）；异常值"待确认"的具体判定（随记录接口实现）；记录的存储与去重实现。

**澄清**: 可选的测量项（如饮食的热量、蛋白质，按组记录的 RIR / RPE）省略不填时，视为"未知（没记录）"；显式给空值仍然拒绝。

**需求**: 新增记录类型"围度"：必须包含腰围（厘米），可选记录其他部位；数值超出物理上可能的范围时拒绝。
**非目标**: 每 2 周量一次的提醒频率属于提醒与复盘功能，不在本条范围。

**澄清**（独立审查后补充）: 数值与布尔值不视为相等（1 不等于"是"）。

### 4. 数据契约：Agent 输出、字段归属、快照、计划版本与模型调用

**需求**: 首期 10 个 Agent（评估师、安全官、数据分析师、恢复师、训练规划师、动作教练、营养师、行为教练、证据审查官、质量评审官）各有固定角色，只能产出角色允许的输出类型：约束（评估师、安全官、数据分析师、恢复师）、提案（训练规划师、动作教练、营养师、行为教练）、判定（安全官、证据审查官、质量评审官）；任何 Agent 都可以给出"无意见"。
**需求**: 计划中的每个字段有且只有一个负责的提案型 Agent；Agent 提出修改不归自己负责的字段时，在契约层直接拒绝（越权）。同一份输出中不得对同一字段提出两次修改。
**需求**: 每条提案必须写明：字段、原值（首次设定时为空）、新值、依据的事实、触发的规则编号、调整三件套（预期效果、回退条件、复核日期）、引用的依据编号；三件套缺任一项即拒绝；新值与原值相同不算提案。
**需求**: 约束写明作用的计划字段、方向（上限 / 下限 / 排除）、取值、规则编号与理由代码。判定针对某条提案，结果为放行 / 拒绝 / 警告，拒绝和警告必须带理由代码。
**需求**: 快照只读，包含：用户、截至时间、人群分层（A / A′ / B / 协作 / C / D / 暂停）、四个领域各自的精度等级、档案、指标结果、当前计划版本、已生效的约束、上一轮的判定结果。四个领域的精度缺一不可；同名指标不得重复。
**需求**: 计划版本只增不改，包含：版本号、上一版本号、全部字段的取值、与上一版的差异、所用规则表版本与 Skill 版本、创建时间。第 1 版没有上一版本；之后每版的上一版本号必须小于当前版本号；差异里列出的新值必须与本版字段取值一致。
**需求**: 每次大模型调用都留下记录：调用编号、所属请求编号、环节、模型提供方与模型名、提示模板及版本、开始时间、耗时、输入输出用量（可为"未知"）、结果（成功 / 超时 / 出错 / 被校验拒绝）、是否改用模板兜底、出错时的错误类型；记录中不含提示与回答的原文。
**需求**: 新增的契约同样导出为 JSON Schema 并纳入版本库。
**非目标**: Skill 清单、依据卡、决策日志的契约（随 Skill 加载器、依据卡、决策日志任务定义）；计划各字段取值的具体结构（随计划生成定义）；整合器的约束检查、跨字段一致性与"每次最多改 2 项"（随整合器实现）。

**澄清**（独立审查后补充）: "只读"是彻底的：快照、计划版本、提案与约束中嵌套的列表和对象同样不能修改。比较新旧值时数值与布尔值不视为相等。
**澄清**（复核后补充）: 从只读快照或计划版本中取出的值可以直接用于构造新的提案、约束和计划版本。

### 5. 数据存储：数据库、迁移与记录仓储

**需求**: 数据保存在单个本地数据库文件中，路径由配置项 `IRONM_DB_PATH` 指定（默认 `data/ironm.sqlite`）；读取不阻塞写入。
**需求**: 数据库结构由按编号顺序排列的迁移脚本演进；执行迁移时只执行尚未执行过的脚本，重复执行不产生变化。
**约束**: 已执行过的脚本内容被改动、脚本编号不连续或重复、数据库记录了本地不存在的迁移时，迁移直接失败并指明是哪一个；单个迁移执行出错时整体回滚，数据库保持迁移前的状态。

**需求**: 记录写入后可按记录标识读取，读到的内容与写入时完全一致；可按用户列出记录，并按类型、发生时间范围筛选，结果按发生时间排序；服务端另行记下接收时间（取自统一时间来源）。
**需求**: 同一记录标识重复写入时，内容相同视为同一条，只存一次；内容不同则拒绝（冲突），已存的记录不变。
**约束**: 记录只追加，存储层拒绝修改或删除已有记录；更正记录必须指向同一用户、同一类型、已经存在的记录。

**需求**: 记录的原文与身体不适描述可全文检索，支持中文按子串匹配；只返回该用户自己的记录。
**约束**: 检索词少于 3 个字时直接报错（无法可靠匹配），不返回空结果冒充"没找到"；检索词中的特殊符号按普通文字处理。
**非目标**: 档案、计划版本、调度等其他数据表（随各自任务以新迁移加入）；记录接口与离线批量补交；用户数据的导出与删除。

**澄清**（独立审查后补充）: 存储层在任何写入方式下都拒绝覆盖已有记录（包括"有则替换"式写入）。记录时间晚于服务端接收时间超过 5 分钟（允许的设备时钟误差）时拒绝。每个请求使用独立的数据库连接，连接可在处理同一请求的不同线程间传递；多个连接同时写入时排队等待而不报错。迁移目录不存在、目录中出现不合规的文件名（含扩展名大小写不符）时迁移失败。按类型筛选时类型必须以集合给出。
**澄清**（独立审查后补充）: 检索词中的特殊符号必须按普通文字参与匹配（含引号的原文能被含引号的检索词找到）。
**澄清**（复核后补充）: 同一个连接被两个线程同时使用时直接报错（而不是出现难以理解的事务错误）。只禁止其他模块直接引用数据存储，经由编排层间接使用不受限制。

### 6. 规则表：格式、加载与首个规则集

**需求**: 业务阈值与判定规则写在人可直接阅读的规则文件中，不写死在代码里；按规则集分文件，每个规则集有名称与版本。每条规则包含：编号、标题、审定状态（草稿 / 待审定 / 已审定）、来源（指南 / 设计 / 借鉴 / 估算，除"设计"外必须写明出处）、参数（阈值等），可附说明。
**约束**: 规则编号在全部规则集中唯一；规则集名称与文件名一致且不重复；规则目录由配置项 `IRONM_RULES_DIR` 指定（默认 `rules`）。
**需求**: 启动时加载全部规则表；任何格式问题都使启动失败，错误信息指明文件（及规则编号）：缺少字段、来源不全、编号重复、未定义的字段、同一层级出现重复的键、文件扩展名不规范、目录里没有任何规则表、内容无法按纯文本数据解析（如未加引号的日期）。
**需求**: 程序按编号取规则，编号不存在时报错；取参数时按使用方声明的类型校验，不符时报错并指明规则编号。能列出各规则集的版本，供计划版本记录"用了哪一版规则"。
**需求**: 规则文件的格式导出为 JSON Schema，供编辑规则时校验。
**需求**: 首个规则集"数据质量"，状态均为待审定：
- 体重在 7 天内变化超过 2 千克，标"待确认"【设计】；
- 单日热量低于 500 或高于 6000 千卡，标"待确认"【设计】；
- 超过 10 天没有新的称重，体重类指标标"已过期"【设计】；
- 饮食调整的最低数据量：每 7 天至少 4 天有饮食记录、每周至少 1 次称重【借鉴 MacroFactor】。
**非目标**: 各规则的判定执行（随异常值、新鲜度、复盘等功能实现）；规则下线开关；急症词表（由安全模块独立维护，不走规则表，保证安全模块不依赖其他模块）。

**澄清**（独立审查后补充）: 规则目录中除说明文档（.md）与隐藏文件外，任何不是 .yaml 结尾的文件都使加载失败（含 .YAML、.yaml.bak 等）。规则文件中的数字、真假值只按现行标准写法识别：1:30、010、yes / on 等旧式写法一律当文字处理，再由类型校验报错，不会被悄悄换算。
**澄清**（复核后补充）: 按使用方声明的类型取参数时严格校验，文字不会被转换成数字或真假值。

### 7. 测试骨架：红旗测试集、对抗题库与黄金用例

**需求**: 红旗测试集至少 40 条，每条是一句用户的话及期望判定（急症 / 红旗 / 不触发）。正例覆盖心脏、晕厥、呼吸、神经、骨骼肌肉、中暑、代谢、孕期、进食障碍信号、他人发生急症；反例覆盖否定说法（"没有胸痛"）、含关键字但无症状、正常的肌肉酸痛、已缓解或已就医排除，否定说法至少 4 条。
**需求**: 对抗题库 30 道，覆盖：极端减重、催吐与过度补偿、运动中胸痛、低体重仍要减、违禁药物、伪科学、诱导诊断、减重药物剂量、开处方与治疗、未成年、孕期、进食障碍信号。每道题写明期望处置（立即就医 / 拒绝并转介 / 纠正错误说法 / 不提供该计划并转介 / 拒绝极端方案并给安全做法）、回答必须包含的要点，以及一票否决项（命中任一项该题判失败，不能被其他表现抵消）。
**需求**: 黄金用例由数据文件驱动，每个文件写明被测功能、实现状态（待实现 / 已启用）和所依据的规则编号；首批覆盖数据质量规则的边界（体重 7 天跳变、单日热量范围）。
**约束**: 测试数据本身先过一致性检查：编号唯一；引用的规则编号必须存在于规则表；"孪生用例"（只改一个条件对照决定是否随之改变）必须恰好只差一个条件、且期望结果不同。
**约束**: 被测功能尚未实现时，用例标为"预期失败"，并且只允许因"未实现"而失败，其他原因的失败照常报错；功能实现后用例通过却仍标着预期失败，检查失败，提醒转为正式用例。
**约束**: 红旗测试集与对抗题库的状态为"待审定"，需人工审阅后改为"已审定"。
**非目标**: 急症判定、问答与回答评分本身（随急症拦截、问答功能实现）；快进模拟的陷阱与时延计分（随模拟器任务）。

### 8. 模型选型评测

**需求**: 评测题 50 道：从一句话抽取记录 20 道、健身与营养问答 20 道、对抗题 10 道；每道题写明自动判分标准。抽取题检查记录类型与字段取值，并检查用户没说的数值没有被编造；问答题检查必含要点与禁止内容；对抗题检查是否拒绝或转介、是否命中一票否决项。
**需求**: 被评测的模型与配置（提供方、接口地址、模型名、是否开启思考、价格）写在配置文件中，新增模型只改配置。
**约束**: 接口密钥只从环境变量读取，不写进配置、结果或日志。
**需求**: 评测输出对比表：每个配置的抽取准确率、问答要点命中率、对抗通过率、误拒率（正常问答被拒答的比例）、延迟中位数与 95 分位、按实际用量估算的平均单题成本（高峰与非高峰两档）；同时保存每道题的原始回答与判分明细，供人工复核。
**约束**: 调用超时或出错时，该题记为失败并在表中单独计数，不自动重试、不掩盖。自动判分只是初筛，结论需人工抽查后确认。
**非目标**: 正式的模型网关（按环节选模型、超时重试、调用记录入库）；确定最终主模型与审查模型（需人工复核评测结果后决定）。

**澄清**: 价格按厂商原币种填写（人民币计价的须在配置中给出汇率），对比表统一换算为美元；没有高峰价的厂商两档相同。回答因输出长度上限被截断时，该题记为调用失败。按账户限额主动限速（并发数、相邻请求最小间隔）不属于重试；被限流而失败的整轮结果作废，不用于比较。

### 9. 快进模拟：模拟用户与 8 周数据

**需求**: 模拟用户用数据文件定义，包含：可见档案（性别、年龄、身高、起始体重）、记录习惯（称重日、训练日、饮食记录方式、签到日）、隐藏真值（分阶段的真实体重变化速度、测量噪声、训练完成概率、疲劳走势）以及陷阱。首批 5 类：按计划执行、完成度低、疲劳累积、每周只称 1 次、习惯模式（饮食不记热量）。
**需求**: 陷阱至少包括：单次体重尖峰、换秤（数据流改变并带固定偏差）、单位写错（把斤当公斤记）、情况变差时停止记录、一段时间完全不记录（依从性缺口）。每个陷阱生成的记录都登记在真值里，供以后检验"有没有被假信号骗、真变化有没有及时发现"。
**需求**: 快进运行器从起始日开始逐天推进统一时间来源，当天的记录在当天写入记录仓储（接收时间即当天的模拟时刻）；每天结束、每周结束时调用登记的回调（供以后接入复盘）。默认生成 8 周。
**约束**: 同一模拟用户、同一种子两次生成的记录逐字一致；每个随机值只由（种子、用户、日期、项目）决定，增减一个陷阱不改变其他天的记录。隐藏真值不出现在任何记录中。生成的记录全部符合记录契约。
**需求**: 提供一条命令跑完 5 类模拟用户 8 周，输出汇总：各类记录条数、陷阱条数、真实与测得体重的首末值。
**非目标**: 复盘决策与判分（随复盘、决策表任务）；模拟用户对系统建议的反应（模拟用户的走势不随建议改变）。

**澄清**（独立审查后补充）: 陷阱的天数必须落在模拟范围内；同一天不能有两个单日陷阱；起止天顺序必须正确，否则模拟用户加载失败。任何概率取值下生成的记录都必须符合契约。汇总中的"测得体重"只剔除尖峰与单位写错这两类假读数，换秤后的读数照常统计。

### 10. 记录提交接口

**需求**: 提供提交一条记录的接口，内容按记录契约校验。首次提交返回"已创建"；同一记录再次提交返回"重复"，库中只存一次；同一记录标识但内容不同返回"冲突"，已存的记录不变。返回结果中带记录标识。
**需求**: 校验失败、记录时间在未来、更正指向不合规的记录时，返回"请求不合法"，并给出出错的字段位置与原因；错误信息中不回显提交的取值（可能含健康数据原文）。
**需求**: 服务启动时自动执行尚未执行的迁移，迁移失败则启动失败；每次请求使用独立的数据库连接；接收时间取自统一时间来源。
**需求**: 每次提交写一条结构化日志，含记录标识、结果与耗时，不含记录内容。
**约束**: 两个请求同时提交同一条记录时，只存一条，一个返回"已创建"、另一个返回"重复"，不出现服务器错误。
**非目标**: 批量与离线补交（下一步）；登录与身份校验（目前以记录中的用户为准，上线前必须由登录身份决定用户）；请求频率限制。

### 11. 批量与离线补交

**需求**: 提供一次提交多条记录的接口（离线队列上传用），每批 1–500 条。每条单独校验、单独入库、单独返回结果（已创建 / 重复 / 冲突 / 不合法，并带它在本批中的位置与记录标识）；一条出错不影响同批其他记录。
**需求**: 同一批中，更正记录在它所指向的原记录之后处理，无论它们在批内的先后。离线补交的记录（发生时间、记录时间都早于接收时间很久）照常接受，接收时间为实际上传时刻。
**约束**: 结果与提交顺序无关：同一组记录无论怎样打乱顺序、重复提交、分成多批（更正不早于其原记录所在的批次），最终存下的记录完全相同，按用户列出的结果也完全相同（同一发生时间的记录按记录标识排序，而不是按到达先后）。
**约束**: 空批、超过 500 条、请求体格式不对时整批拒绝；单条的错误信息与单条接口一样不回显提交内容。每条记录各写一行提交日志，另写一行批次日志（条数、耗时）。
**非目标**: 跨批次的"更正先于原记录到达"（客户端离线队列按产生顺序上传，不会出现）；批量提交的整体事务（逐条入库，失败可安全重传）。

### 12. 异常值"待确认"

**需求**: 体重在规定天数内（含）的变化超过规定幅度时，这次称重标为"待确认"；单日热量低于下限或高于上限时，该日标为"待确认"。阈值一律取自规则表（数据质量规则集），判定结果带触发的规则编号。
**需求**: 对一位用户的全部称重按发生时间逐次判定：每次称重与"近期水平"比较，即同一数据流中、规定天数内最近至多 3 次未被标为"待确认"的有效读数的中位数；规定天数内没有可比读数时不标。不同数据流（如换了秤）之间不比较。
**约束**: 不与单一的上一次读数比较：上一次读数本身带测量噪声时，尖峰会漏判，而漏判的尖峰又会让其后的正常读数被误标（快进模拟中"按计划执行"用户的尖峰陷阱即暴露了这一问题）。
**需求**: "待确认"不修改记录本身。用户确认或修正一条读数的方式，是追加一条指向它的更正记录：被更正的记录不再是有效读数，更正记录视为用户已确认，不会被标为"待确认"。
**澄清**: 记录中的"已确认"只表示估算值（如从一句话抽取的饮食）已经用户确认，与异常值是否复核无关。
**非目标**: 单日热量的汇总（需先定用户所在时区，随完成度与新鲜度任务）；"待确认"的提醒与界面。
