### 1. 冲刺 3 范围与默认场景

**需求**: 冲刺 3 交付在线问答链路：用户发一句话，服务端给出安全、有依据、按统一结构组织的回答。默认场景为健身（训练知识、动作技术、营养、恢复、习惯、身体不适、补剂、计划相关）；只有用户选了减脂目标时，回答与计划才涉及热量缺口。
**约束**: 每条消息必须先经过服务端急症检查与拒答检查；后面的任何环节出错，都不影响这两道检查及其回答。
**非目标**:
- 不做向量级意图识别。
- 不做 L2 多专家会审、L3 真人专家。
- 不做调度、盲审、终审、复盘与快进模拟，这些顺延到冲刺 4。
- 不做手机端界面与 App 离线版。

**需求**（架构定稿）: 产品的智能部分分两条链路，功能 Agent 出现在这几处：
- 管家对话：用户的跨功能、需全面判断的提问只经管家，管家理解问题、调度专业 Agent、组织回答。
- 功能页提问：就本功能内容提问，直接调用本功能的专业 Agent。
- 计划链路：第一版计划与之后的计划调整，由各专业 Agent 提案，经综合、审查后发布。

**非目标**（顺延到冲刺 4）:
- 对话回答里的操作按钮（如“替换今日动作”）。
- 每日简报。

### 2. 模型接入

**需求**: 每个环节（意图识别、回答、记录抽取等）单独配置所用模型；模型服务的地址、模型名、超时时间都写在配置里，密钥只从环境变量读取。
**需求**: 单次调用超时或出错时，最多重试 1 次。仍然失败、或输出没通过格式校验时，按"失败"处理并使用兜底，兜底方式见 §6。整条请求不因此报错。
**需求**: 每次调用都留一条记录，内容为请求编号、环节、服务商、模型、提示模板版本、耗时、用量、状态、是否用了兜底。
**约束**:
- 调用记录与日志都不含提示词、用户原话或回答原文。
- 密钥不进入配置文件、记录与日志。
- 可以换用任何兼容常见对话接口的模型服务。

### 3. 对话入口与安全前置

**需求**: 提供对话接口：接收用户的一句话，返回回答与本次请求编号。
**需求**: 每条消息先过急症检查与拒答检查：
- 判为急症或红旗时，直接返回审定过的四段式回答，不调用模型。
- 命中拒答时，返回对应的拒答模板，再接正常回答中允许的部分。
**需求**: 区分本人与旁人。说的是别人发生急症（如"看到有人晕倒了""我爸突然倒地"）时，照常给出急救指引，但不给本人记安全标记、不暂停本人的计划；拿不准是谁时按本人处理。
**需求**: 说的是本人的急症或红旗时，给本人记一条安全标记（只含时间、级别、条目编号、类别，不含原话）。之后的计划按 [2026-10-20] 中暂停、确认就医的规则执行。
**约束**: 急症检查不依赖模型、知识库或网络以外的任何服务，模型全部不可用时照常工作。

**需求**: 提问有两个入口。管家对话是全面回答的入口；训练、饮食、恢复、指标及档案四个功能页，也可以就本功能的内容提问，直接调用该功能对应的专业 Agent。
**修正**（当日）: 本条取代本节此前“管家对话是唯一提问入口、四个功能页不提供提问”的写法。
**需求**: 功能页的提问与管家提问遵循同一套安全前置：先过急症与拒答检查，命中即返回审定的回答，不调用模型。
**需求**: 功能页的提问只调用本功能的专业 Agent 与安全官，不调用其他功能的 Agent，也不经过管家调度。跨功能、或请求全面判断的问题，转入管家对话并带上上下文。
**需求**: 从功能页的某一项提问或进入对话时，带上所看内容的标识（所在功能、哪一项，例如“今日训练 · 第 3 个动作 · 第 2 组未完成”）。该标识作为意图识别与调度的参考，用户不必重新描述。
**约束**:
- 带入的标识不包含用户原话，也不替代急症检查与拒答检查。
- 标识只能提高安全判定，不能降低。例如在训练页说“胸口疼”，照常判为急症。
**需求**（训练中升级）: 带着训练页上下文（或在训练页提问）时，心血管、呼吸、晕厥三类红旗按急症处理（条目 EM-EXERTIONAL），因为这时症状出现在运动中。其他类别（如关节）不升级；不在训练页时照常按原级别处理。
- 同一个问题从任一入口提问，安全判定与引用的数字必须一致。

### 4. 意图识别

**需求**: 把每句话识别为一个意图及其所属领域，并给出置信度。意图集合覆盖：
- 训练知识、动作技术、营养饮食、个人数据解读、恢复睡眠、习惯动机、养生保健
- 身体不适、补剂药物、特殊人群、计划相关、记录、闲聊、超范围
**需求**: 先按规则识别，再用模型识别，两者合并得出结果。安全方向只升不降：任一方认为涉及身体不适、特殊人群或红旗，结果就按更严的处理。模型不可用时用规则的结果。
**需求**: 置信度低、又无法归入任何领域、且消息长度超过 2 个字时，返回 1 个澄清问题，不硬答。
**需求**: 意图识别不出来、但审定的问答卡命中时，按卡所属的意图回答，不追问。
**约束**: 意图识别不改计划，也不写入画像。

### 5. 编排

**需求**: 按意图选出主 Agent，必要时加最多 2 个辅助 Agent。比如问动作时膝盖疼，就以动作教练为主、安全官辅助。安全官对每条路由都参与，并能给出约束。
**需求**: 同一阶段的 Agent 并行运行，互相看不到对方的输出；下一阶段只看到上一阶段汇总后的结果。
**需求**: 单个 Agent 出错或超时时，降级为"本次无意见"，其余照常；主 Agent 失败时退到下一层回答（见 §6）。
**需求**: 每次请求的运行记录可以回放：哪些 Agent、哪些 Skill 版本、各自输出类型、用了哪些工具、耗时多少，记录中不含用户原话。
**约束**: 每个 Agent 只能调用白名单里的工具；问答环节的任何 Agent 都不能直接改计划，需要改计划的问题只作说明，并标为"需进入计划调整"。

**澄清**: 本节中的“主 Agent”指本次回答的主责专业 Agent（如动作教练）。管家位于其上，是对话的主 Agent，负责调度。
**需求**: 路由按“领域打分”决定主责与辅助，而不是命中一个关键词就选一个 Agent：
- 按意图、命中的关键词、识别出的关注点，给每个专业 Agent 打分；
- 分数最高者为主责；辅助 Agent 取分差不超过主责一定比例的其他 Agent，最多 2 个；
- 分数接近时同时列为辅助，而不是只取一个；
- 安全相关的关注点（身体不适、特殊人群）只提高相关 Agent 的分数与参与的必然性，不因分数低而被排除。
**需求**: 每次路由都记录：各 Agent 的得分、主责与辅助、理由代码、是否降级。理由代码取自固定词表，不外露用户原话。
**约束**: 分数、阈值、辅助比例写在规则表中并可审定；端口、模型名等不进入规则表。
**需求**: 管家决定本次调用哪些专业 Agent、以什么顺序调用，并给出理由代码。管家的调度结果必须通过以下校验，才会执行：
- 只能从白名单中的专业 Agent 里选，主责 1 个、辅助最多 2 个。
- 安全官必须参与。
- 同时涉及恢复与训练时，恢复先于训练执行。
- 证据审查官、质量评审官不能在问答中被调用。
- 辅助 Agent 的加入必须有依据：管家给出的辅助，要么在领域打分中达到门槛，要么有明确的关注点理由。无依据的辅助不执行。

**需求**: 部分成功如实标注。并行执行时，主责成功、辅助失败或超时，回答标明这次只包含部分建议，运行记录写明哪一路失败。不得把缺了一路的回答当作完整回答。
**需求**: 同一请求内，针对同一对象的写操作只执行一次。重复的写操作被拒绝并记录，避免一次请求里重复入账。

校验不通过时，丢弃管家的调度，改按规则路由表执行，并在运行记录里标明。
**需求**: 管家不能直接写计划、记录或画像。它只能：组织回答；把问题标为“需进入计划调整”；按 §8 生成画像候选。
**需求**: 快速通道。意图明确、只涉及单一领域、置信度达标时，按规则路由表直接调用主责 Agent，跳过管家的调度。模型不可用时，所有问题都走规则路由表。
**需求**: 运行记录写明本次调度的来源（管家调度、快速通道、校验失败后改用规则路由表），以及管家给出的理由代码。
**约束**: 调度与快速通道都不改变 §3 的安全前置顺序。

### 6. 问答分层与回答结构

**需求**: 回答分三层：
- S 安全通道：规则直接处理（§3）。
- L0 标准答案：已审定的问答卡，覆盖高频、低风险的问题。命中时优先使用。
- L1 单专家：一个 Agent 加载 Skill 作答，结论来自审定的知识与规则，模型只负责表达。
**需求**: 回答按统一结构组织：结论 → 针对你 → 为什么 → 怎么做 → 注意（何时停止或就医）→ 不确定的地方。不适用的部分省略。回答类型分为直接、个性化、条件、澄清后、转介五种。
**需求**: 降级要告诉用户。L1 失败时退到 L0，再退到一般建议或转介。降级永远不跳过安全检查，单次请求最多重试 2 次。
**需求**: 安全类问答卡由安全官负责，覆盖极端减重、过度补偿、体重过低、违禁药物、减重药物剂量、诱导诊断、开药与治疗、未成年、孕期、进食障碍信号和常见健康误区。安全官每条路由都参与，所以这些卡总能被查到；命中时优先使用，即使用户在要计划（"帮我安排 7 天断食"）也先按卡回答。安全官的卡已为这类情况审定，直接使用，安全提示附在后面。
**需求**: 健康错误信息防护：
- 违禁药物、极端节食、伪科学疗法：拒绝，说明风险，给替代做法。
- 证据强弱不同的说法不等同呈现，没有可靠依据时明说"没有可靠证据"。
**约束**: 引用只能来自知识库与规则表；回答中不出现诊断、处方、治疗方案。

### 7. 数字校验

**需求**: 回答中的每个数字（次数、组数、分钟、千卡、克、心率、体重等）都必须能对应到一个登记过的来源：用户自己的记录与计算结果、规则表参数、动作库、问答卡。
**需求**: 出现没有来源的数字时，拦截这条回答并重写一次；重写后仍不合规，就去掉这些数字，或改用模板回答，并在记录里标明。
**约束**: 日期、序号这类不属于建议的数字不参与校验。
**需求**: "针对你"：用户在这句话里说的身高、体重或 BMI，按规则算出 BMI 写进回答，例如"按你说的身高 165 厘米、体重 45 公斤，BMI 约 16.5"。这些数字视为登记过；它们只用于本次回答，不写入运行记录。

### 8. 对话记忆

**需求**: 每次回答前读取上下文：最近的消息、较早对话的摘要、画像中与本次意图相关的部分。
**需求**: 一段对话达到 15 条消息时，把较早的部分压缩成摘要，最近的消息保留原文。
**需求**: 从对话中发现的画像变化（新的身体状况、器材、可练天数、偏好等）只作为候选：用户确认后才写入画像。例外是会让分层变严的信息（如新报告的心脏病、怀孕、进食障碍信号），它立即生效，同时请用户确认。
**约束**: 画像更新在回答之后异步进行，不拖慢回答；没有确认的候选不进入长期记忆。

### 9. 冲刺 3 验收

**需求**:
- 对抗题库（30 题）全部通过。
- 模型全部不可用时，对话仍能返回安全检查、问答卡或模板回答。
- 一次完整对话（建档后提问、追问、报告不适、旁人急症）的运行记录可以回放。
- 模型全部不可用时，四个功能页的内容照常显示与更新。

### 10. 功能页数据

**需求**: 训练、饮食、恢复、指标及档案四个功能页，只展示三类内容：总计划、用户记录，以及由规则与计算得出的结果。例如：
- 训练：今日训练单、每组目标、替代动作、动作要点。
- 饮食：热量与蛋白目标、当天剩余。
- 恢复：今日精力与减量。
- 指标及档案：趋势、可信范围、精度、还差什么、依据卡。

**需求**: 用户在功能页上的操作（记一组、记一餐、选精力等）只写入记录并触发重新计算，页面随之更新；这类操作不调用 Agent。
**需求**: 功能页可以就本功能提问（见 §3），由本功能的专业 Agent 作答；提问以外的情况不调用 Agent。
**需求**: 功能页遇到需要判断、但超出本功能范围的情况（例如记录里写了“膝盖疼”），提供转入管家对话的入口，并按 §3 带上上下文。
**需求**: 照片与视频作为功能页的输入时，由该功能对应的识别能力产出候选内容；候选经用户确认后才入账，未确认的不进入计算与回答。识别不确定时不给结论，只请用户补充。视频中的动作分析属于后续阶段，届时同样只产出候选。
**需求**: 识别与提问分开处理。识别只产出候选数据，不产出建议；识别能力不可用时，自动退回手动填写，记录与页面照常可用。
**约束**: 识别不可用时页面不报错，只在对应位置说明“暂时无法识别，请手动填写”。识别过程的失败不影响安全前置与已存数据。
**约束**:
- 功能页上的数字与管家回答中引用的同一数字一致。
- 安全规则对功能页的记录与提问照常即时生效。
- 功能页的提问不能修改总计划、记录或画像；需要调整的，按 §5 标为“需进入计划调整”。
- 同一内容从两个入口提问，安全判定与引用的数字一致。

### 11. 信号收件箱

**需求**: 由规则检测值得管家主动提起的情况，生成信号。首批信号包括：
- 连续 3 天精力为最低档。
- 同一动作连续 2 次训练未完成。
- 体重趋势达到判断条件，且方向与目标相反。
- 记录中提到身体不适，但不属于急症。

每条信号含：编号、类别、级别、事实依据（记录与计算结果的标识）、生成时间，不含用户原话。
**需求**: 用户下次打开管家对话时，管家先提起最高级别的 1 条未处理信号，再回答用户的问题。用户处理后，或明确表示忽略后，该信号关闭。
**需求**: 同类信号关闭后，在冷却期内不再生成。冷却期与各信号的阈值写在规则表中，待审定。
**约束**:
- 急症与红旗不走信号，仍按 §3 即时处理。
- 信号由规则判定，不由模型判定。
- 管家提起信号时不能改计划；需要调整的，按 §5 标为“需进入计划调整”。
**非目标**: 推送通知（放到冲刺 4，与每日简报一起做）。
**非目标**: 回答质量的人工评分（随冲刺 4 盲审）。

### 12. Agent 的组成与问答链路（项目负责人决定）

**修正**（当日）: 本节取代本节此前"快照 + 各 Agent 并行出意见"的写法，也取代"问答类 Skill"的做法：问答不使用 Skill。

**需求**（Agent 的组成）: 每个专业 Agent 由五样东西组成，各 Agent 之间的区分体现在全部五样上，不只是知识库：
- 职责与权限：负责哪个领域、能对哪些计划字段提案、能否下约束；问答里决定它能说什么、不能说什么。
- 知识库：本领域的资料，按领域打标签存放在同一个库里。
- 能读的数据：共享快照里允许它看的部分。
- 工具：可调用的计算与查询。
- Skill：计划链路里的决策规则。

**需求**（工具与 Skill 的分工）:
- 工具负责"算事实、查事实"，例如热量目标、BMI、体重趋势、动作库的替代动作、分层判定。工具是确定性的、有测试，问答与计划共用同一份实现。
- Skill 负责"该怎么办"：调用工具并按规则参数，产出计划链路的提案或约束，需要审定。
- 凡是算事实的逻辑都放进工具，不写在 Skill 里面，保证问答与计划给出的同一个数字一致。

**需求**（问答链路）:
1. 安全前置：急症词表 + 模型复核（只升不降）、拒答检查、本人 / 旁人；急症直接返回。
2. 理解：意图、关注点、领域打分（主领域 1 个、相关领域最多 2 个）。
3. 分两条路回答：
   - 基本通用问题：由通用 Agent 直接回答，不检索。包括打招呼、闲聊、App 怎么用、鼓励与陪伴、概念解释（如"什么是 BMI"）。通用 Agent 不给具体的训练量、热量、剂量等数字。
   - 专业领域问题：涉及具体的训练、饮食、恢复、身体状况建议时，由涉及的每个领域 Agent 各自完成"召回（关键词 + 向量）→ 重排 → 基于检索结果生成意见（带出处）"，并可调用本领域的工具、读取快照中允许的数据。带"身体不适""特殊人群"关注点的一律走这条路。
   - 拿不准属于哪条路时，走专业流程。
4. 整合：只涉及一个领域时，该 Agent 的意见即为回答；涉及多个领域时，由管家整合成一个回答。
5. 安全官每次都参与：它的约束与提醒必须写进回答，冲突时以它为准。

**需求**（依据与数字）:
- 专业回答的结论必须能指到检索到的段落或工具的计算结果。
- 回答中的数字只能来自检索到的段落、工具的计算结果或快照。
- 检索不到相关依据时，明说"没有找到可靠依据"，不凭模型自己的记忆回答。
- "针对你"的个人数字（如按体重算的蛋白质）只能来自工具与快照。

**需求**（兜底）:
- 命中安全类问答卡时，直接用卡回答。
- 模型不可用时用问答卡；没有卡时给一般说明。
- 问答卡并入知识库，作为人工精选、优先级最高的条目。

**需求**（计划链路）: Agent 运行自己的 Skill 出提案与约束，使用同一份快照；整合器检查一致性，不一致的退回重做（最多 2 轮）；管家把发布的结果合成一段说明。

**约束**: 知识库的内容须有来源与审定。仓库是公开的，有版权的原文不进仓库，也不整段展示给用户。

**澄清**（实现时补充）:
- 知识库资料目录由配置项 `IRONM_KB_DIR` 指定（目录不进仓库）；不设时知识库只含问答卡与动作库。
- 问答卡的触发词命中时，该卡作为人工精选的条目在本领域优先召回。
- "同一个工具"指同一份计算：问答的工具与计划的 Skill 都调用这份计算；Skill 所在层次低于工具，直接调用计算而不经过工具。
- 相关领域检索不到依据时不发言，不提示"部分建议"；主领域没有意见、或有 Agent 出错 / 作答失败时才提示。
- （独立审查后）数字校验覆盖意见的每一部分（结论、推理、做法、注意、不确定），只有依据算数字的来源；中文数字的常见写法（两三组、三到五组、百分之八十、一千五、两万步）都算数字。
- （独立审查后）打招呼或问 App 用法时，这句话里提到身体不适或特殊人群，也走专业流程；画像里已有的健康状况不改变闲聊的走向。
- （独立审查后）工具的计算只在问题与它有关时才算依据（问体型才算 BMI，问吃多少才算热量目标）；Agent 判断依据答不了这个问题时，该领域不发言。
- （独立审查后）回答整合后，"针对你"的计算原样保留；外部资料只展示出处与不超过 80 字的摘录，回答里也不能整段照抄外部资料（连续 40 字相同即作废）；问答卡与动作库可完整展示。外部资料的编号不能冒用问答卡、动作库的编号。
- （复核后）功能页上转回管家对话时，这句话里的身体不适 / 特殊人群提醒照样给出。

**非目标**:
- 信号收件箱（§11）与功能页数据展示（§10）暂缓。
- 急症词表暂不删减。

#### 12.1 定稿补充（项目负责人逐条确认）

**Supersedes**: 本节上文以下几处：
- “Skill：计划链路里的决策规则”与“问答不使用 Skill”——改为下文“Skill 按需装载”；
- “涉及多个领域时，由管家整合成一个回答”中管家只负责整合——改为下文“管家调度 + 整合”；
- “计划链路”单列一条——改为下文“计划与问答合并为一条链路”；
- [2026-10-21] §3 中“功能页提问直接调用本功能的专业 Agent”保留，并在下文明确为单独路径。

**需求**（Skill 按需装载）:
- 问答与计划都会判断要不要装载 Skill，判断条件为：所属 Agent、意图、场景、人群分层。匹配就装载，不匹配就不装载。
- 不装载 Skill 也能回答：Agent 照常检索本领域知识、调用工具、生成意见。Skill 是增强，不是前提。
- 问答里只用 Skill 的说明部分：放进该 Agent 的生成提示，规定怎么判断、按什么顺序、做到哪为止。计划里说明与代码都用，代码负责算数并产出提案或约束。
- 处方类 Skill 不装载给不可给计划的分层，这一点由装载规则保证，不靠提示词。

**需求**（管家：调度 + 整合）: 调度由领域打分与管家共同完成：
1. 先做领域打分，得到候选的领域 Agent 与得分。
2. 只涉及一个领域、且置信度不低于规则表门槛时，走快速通道：直接按打分结果调用，不经管家调度。
3. 其余情况由管家（模型）从候选中决定调用哪些 Agent、按什么顺序，并给出理由代码。
4. 管家的调度结果须通过规则校验，才会执行：只能从白名单中选；主责 1 个、辅助最多 2 个；安全官必须参与；同时涉及恢复与训练时恢复先执行；问答中不能调用审查类 Agent。校验不通过，或模型不可用时，改按领域打分的结果执行，并在运行记录里写明。
5. 各 Agent 意见出来后，涉及多个领域时由管家整合成一个回答：主责在前；安全官的约束与提醒必须写入，冲突时以它为准；缺哪一路要标明。
- 管家不能直接写计划、记录或画像。

**需求**（功能页提问：单独路径）: 功能页上的提问不经过管家：只调用本功能对应的 Agent 与安全官，安全前置照常。问到本功能以外的内容时，转入管家对话，并带上当前上下文。本功能 Agent 的作答方式与管家对话中相同（检索 + 工具 + 按需装载 Skill），同一个问题从两个入口问，依据与数字一致。

**需求**（计划与问答合并）: 计划与问答走同一条链路：安全前置 → 理解 → 调度 → 各 Agent 作答（检索 + 工具 + 按需装载 Skill）→ 管家整合。之后按请求类型分开：
- 问答：输出回答与依据，做数字校验，不写入任何数据。
- 计划：输出计划草案，依次经过约束复核、盲审、终审，通过后写入新的计划版本。
第一版计划也走这条链路；调度结果必须包含生成计划所需的 Agent，并保持“安全官的约束先于提案”的顺序。

**非目标**: 知识库补充指南原文，以后再定。

### 13. 问答召回与大模型优先（项目负责人决定）

**Supersedes**: 本日 §12"兜底"中"命中安全类问答卡时，直接用卡回答"与"问答卡并入知识库，作为人工精选、优先级最高的条目"两条；§12"澄清"中"问答卡的触发词命中时，该卡作为人工精选的条目在本领域优先召回"一条。

**需求**（大模型优先，回答不了才降级）:
- 问答的回答都由大模型基于依据生成。大模型回答不了（不可用、输出不合规、依据不够）时才逐级降级：工具算出的事实 → 问答卡 → 固定说法。降级发生在哪一步写进运行记录。
- 命中安全类问答卡时不再直接用卡回答：安全类卡是安全官的知识，由安全官基于它生成带依据的意见；安全官的意见必须写进最终回答，冲突时以它为准。大模型回答不了时，才降级为直接用这张卡。
- 急症与拒答仍用固定的回答模板，不交给大模型生成，保证稳定、离线可用。

**需求**（多查询改写）:
- 专业问题检索前，先由大模型把用户这句话（结合最近几轮对话与功能页上下文）改写为一条主查询和几条不同说法，条数上限见规则表；一句话里问了几件事时拆开。
- 改写只能补全指代、拆分、换说法，不能加入用户没说过的事实或数字；用户说到的身体不适、特殊人群相关内容不能丢。不符合时改写作废，只用原话。
- 主查询同时交给意图识别；急症判断只看用户原话。
- 改写不可用时只用原话。

**需求**（两路召回与融合）: 每条查询在相关领域内各走两路召回：关键词检索与向量检索。所有查询、所有路的结果按排名融合、去重，取候选（数量见规则表）。向量服务不可用或未配置时只用关键词一路。

**需求**（大模型重排）: 由大模型按"这一段能不能回答这个问题"给候选打分，保留不低于门槛的前几条（数量与门槛见规则表）。重排不可用时按现有的覆盖比例打分。

**需求**（问答卡优先级最低）: 本领域有其他过门槛的依据时，问答卡不作为依据；只有没有其他依据时，问答卡才参与作答。

**约束**:
- 发给向量服务的只有查询文字与知识库段落，不含画像与对话记录；向量服务与其他模型服务一样在模型配置中列出，密钥只从环境变量读取。
- 运行记录只写查询条数、各路召回的段落编号与重排分数，不写查询原文。
- 每次专业问答增加的模型调用：改写 1 次，每个作答领域重排 1 次；各领域并行。
- 知识库段落的向量可以缓存，段落内容变化后重新计算。

**澄清**（实现时补充）:
- 命中触发词的安全类卡一定进入安全官的依据，不会因召回或重排漏掉；安全官有意见时放在回答最前。
- 问答卡作为最低优先级的依据：本领域没有其他依据时，触发词命中的卡参与作答（大模型重排已判为无关的除外）。降级到问答卡时，触发词命中的卡优先；安全官只能降级到触发词命中的安全类卡，此时其他领域只保留"针对你"的计算结果。
- 安全官每次都参与，它没有可说的不算"部分建议"。
- 明显是打招呼、问 App 用法或超范围、且没有提到身体不适 / 特殊人群的话，不做改写。
- 大模型重排不可用时的打分不计问句里的虚词（怎么、多少、吗等），知识库里从没出现过的词按最高权重计入。
- 向量服务第一次用到时计算知识段落的向量；失败后隔一段时间（默认 5 分钟）再试，期间只用关键词一路。
- 用户在这句话里给了身高体重时，即使作答的领域里没有会算 BMI 的，也照样算出 BMI 给用户。

**修正**（独立审查后）:
- **Supersedes** 本节"主查询同时交给意图识别"：意图按用户原话（结合最近几轮）识别；原话含糊、像闲聊或超范围时，再看改写后的主查询，只有它是专业问题时才采用。改写不能把专业或安全问题降成闲聊。

- （复核后）段落向量与关键词检索用同样的文本：标题、正文和口语关键词。
- 向量服务收到的查询可能带有从最近几轮补全的指代内容；不发送画像。

**非目标**: 实体词典、假设答案（HyDE）等其他召回路暂不做。

### 1. 工程约束：模块依赖方向

**需求**: 业务模块按层次组织（从上到下大致为：对外接口 → 编排与审查 → 各专业 Agent → Skill → 计算 / 指标 / 安全规则 → 共享契约与基础设施），只允许上层依赖下层，禁止下层反向依赖上层。
**需求**: 安全规则模块（急症拦截、人群分层等）除共享契约与基础设施外，不得依赖任何其他业务模块，保证在离线或模型不可用时仍能独立运行。
**需求**: 数据存储只能被编排、审查和对外接口这几层直接使用；Agent、Skill 和计算层不得直接读写存储，只能使用上层传入的数据。
**需求**: 任何违反上述规则的依赖都使项目的标准检查失败（本地提交前检查与持续集成两处一致），失败信息指明违规的调用方与被调用方。
**约束**: 每个业务模块都必须在分层规则中有明确位置；新增模块未登记分层时同样检查失败，避免绕过约束。
**非目标**: 不限制对第三方库的依赖；不检查测试代码的依赖方向。

**澄清**（独立审查后收紧）: 数据存储只能被编排层与对外接口直接使用；调度、记忆等模块需要持久化时，通过契约中定义的数据访问接口，由上层注入实现。

### 2. 工程基础：时间、标识、配置与日志

**需求**: 系统内所有"当前时间"都取自同一个可替换的时间来源；测试与快进模拟可以把时间固定在某一时刻，或向前拨动。
**约束**: 时间一律带时区，统一按 UTC 表示与比较；不带时区的时间在进入系统时被拒绝（报错，不做猜测）。

**需求**: 服务端生成的标识全局唯一；测试与模拟可指定种子，使同一流程两次运行得到完全相同的标识序列。

**需求**: 运行配置通过 `IRONM_` 前缀的环境变量提供，当前配置项：`IRONM_ENV`（`dev` / `test` / `prod`，默认 `dev`）、`IRONM_LOG_LEVEL`（`debug` / `info` / `warning` / `error`，默认 `info`）。
**约束**: 出现未知的 `IRONM_` 变量或取值非法时，启动直接失败，错误信息指明是哪个变量；不静默忽略、不回退到默认值。

**需求**: 日志为结构化格式，每行一条记录，包含时间、级别、来源、事件名和附加字段；日志时间取自上述同一时间来源。
**约束**: 日志不得包含健康数据原文：事件名必须是固定的标识性名称而非自由文本；附加字段只允许标识类（各种 ID）和运行类信息（状态、耗时、计数、错误类型等），写入其他字段时直接报错；记录异常时只记异常类型，不记异常消息内容。

**需求**: 在固定时间和固定种子下，同一流程两次运行产生的标识与日志逐字一致。
**非目标**: 用户本地时区换算（随记录与复盘功能定义）；日志中对数据内容做哈希（首次需要时再定方案）；日志落盘与轮转。

**澄清**（独立审查后补充）: 日志附加字段的取值也受限：标识类与状态类取值只能是不含空格与中文的短标识，路径不得带查询参数；不经结构化接口、直接写入的日志只输出"拒绝了一条不合规日志"及其来源，不输出其内容。配置项名必须全大写，大小写不同的同名配置视为未知配置而失败。
**澄清**（复核后补充）: 取值格式校验只能挡住含中文、空格、查询参数的文字，挡不住英文单词（如 `chest_pain`）；标识类字段只应传入系统生成的标识，这一点靠代码审阅保证。

### 3. 数据契约：记录、缺失值与指标结果

**需求**: 所有记录使用统一结构：记录标识（由客户端生成，用于去重）、用户、记录类型、发生时间、记录时间、来源（用户 / 设备 / 估算）、是否已确认、原文（用户原话或设备原始字段，可空）、规整后的内容；可选附带客户端提示的精度等级。
**需求**: 首批记录类型：训练打卡、按组记录、称重、每周签到、饮食、身体不适、基线测试。每种类型的规整内容字段固定，单位统一（千克、千卡、克）；内容与类型不匹配时拒绝。
**需求**: 记录只追加不修改；改错是追加一条同类型的更正记录，指向被更正的记录。
**约束**: 发生时间不得晚于记录时间；时间必须带时区；来源为设备时必须注明数据流（不同设备的数据不混算）；数值超出物理上可能的范围时拒绝（如体重不在 20–400 千克）；出现未定义的字段、非有限数字（NaN、无穷）或以文本形式给出的数字时拒绝。这些都在入口直接报错，不做纠正或猜测。

**需求**: 缺失值必须显式标为"未知"并注明原因（没记录 / 不愿提供 / 无法解析 / 数据不足），禁止用 0 或空值代替。
**约束**: "未知"不能参与算术运算，也不能当真假值判断，误用时直接报错。

**需求**: 指标结果包含：指标名、所属领域（训练 / 体重与体成分 / 饮食 / 恢复）、数值或"未知"、单位、可信范围（下限、上限、置信水平）、精度等级（P0–P3）、使用的记录条数、窗口天数、状态（正常 / 数据不足 / 已过期 / 待确认）、还差什么、最近一条记录的时间、计算时间、所用公式编号。
**约束**: 字段之间必须一致，否则拒绝：状态为正常时必须有数值；数值为"未知"时不得有可信范围，状态也不能是正常；可信范围的下限不大于上限且包含数值；状态为数据不足时必须说明还差什么。

**需求**: 全部契约可导出为 JSON Schema 文件并纳入版本库；契约改动后未重新导出时，标准检查失败。
**非目标**: 快照、Agent 输出、计划版本、字段归属、模型调用记录（下一步）；异常值"待确认"的具体判定（随记录接口实现）；记录的存储与去重实现。

**澄清**: 可选的测量项（如饮食的热量、蛋白质，按组记录的 RIR / RPE）省略不填时，视为"未知（没记录）"；显式给空值仍然拒绝。

**需求**: 新增记录类型"围度"：必须包含腰围（厘米），可选记录其他部位；数值超出物理上可能的范围时拒绝。
**非目标**: 每 2 周量一次的提醒频率属于提醒与复盘功能，不在本条范围。

**澄清**（独立审查后补充）: 数值与布尔值不视为相等（1 不等于"是"）。

### 4. 数据契约：Agent 输出、字段归属、快照、计划版本与模型调用

**需求**: 首期 10 个 Agent（评估师、安全官、数据分析师、恢复师、训练规划师、动作教练、营养师、行为教练、证据审查官、质量评审官）各有固定角色，只能产出角色允许的输出类型：约束（评估师、安全官、数据分析师、恢复师）、提案（训练规划师、动作教练、营养师、行为教练）、判定（安全官、证据审查官、质量评审官）；任何 Agent 都可以给出"无意见"。
**需求**: 计划中的每个字段有且只有一个负责的提案型 Agent；Agent 提出修改不归自己负责的字段时，在契约层直接拒绝（越权）。同一份输出中不得对同一字段提出两次修改。
**需求**: 每条提案必须写明：字段、原值（首次设定时为空）、新值、依据的事实、触发的规则编号、调整三件套（预期效果、回退条件、复核日期）、引用的依据编号；三件套缺任一项即拒绝；新值与原值相同不算提案。
**需求**: 约束写明作用的计划字段、方向（上限 / 下限 / 排除）、取值、规则编号与理由代码。判定针对某条提案，结果为放行 / 拒绝 / 警告，拒绝和警告必须带理由代码。
**需求**: 快照只读，包含：用户、截至时间、人群分层（A / A′ / B / 协作 / C / D / 暂停）、四个领域各自的精度等级、档案、指标结果、当前计划版本、已生效的约束、上一轮的判定结果。四个领域的精度缺一不可；同名指标不得重复。
**需求**: 计划版本只增不改，包含：版本号、上一版本号、全部字段的取值、与上一版的差异、所用规则表版本与 Skill 版本、创建时间。第 1 版没有上一版本；之后每版的上一版本号必须小于当前版本号；差异里列出的新值必须与本版字段取值一致。
**需求**: 每次大模型调用都留下记录：调用编号、所属请求编号、环节、模型提供方与模型名、提示模板及版本、开始时间、耗时、输入输出用量（可为"未知"）、结果（成功 / 超时 / 出错 / 被校验拒绝）、是否改用模板兜底、出错时的错误类型；记录中不含提示与回答的原文。
**需求**: 新增的契约同样导出为 JSON Schema 并纳入版本库。
**非目标**: Skill 清单、依据卡、决策日志的契约（随 Skill 加载器、依据卡、决策日志任务定义）；计划各字段取值的具体结构（随计划生成定义）；整合器的约束检查、跨字段一致性与"每次最多改 2 项"（随整合器实现）。

**澄清**（独立审查后补充）: "只读"是彻底的：快照、计划版本、提案与约束中嵌套的列表和对象同样不能修改。比较新旧值时数值与布尔值不视为相等。
**澄清**（复核后补充）: 从只读快照或计划版本中取出的值可以直接用于构造新的提案、约束和计划版本。

### 5. 数据存储：数据库、迁移与记录仓储

**需求**: 数据保存在单个本地数据库文件中，路径由配置项 `IRONM_DB_PATH` 指定（默认 `data/ironm.sqlite`）；读取不阻塞写入。
**需求**: 数据库结构由按编号顺序排列的迁移脚本演进；执行迁移时只执行尚未执行过的脚本，重复执行不产生变化。
**约束**: 已执行过的脚本内容被改动、脚本编号不连续或重复、数据库记录了本地不存在的迁移时，迁移直接失败并指明是哪一个；单个迁移执行出错时整体回滚，数据库保持迁移前的状态。

**需求**: 记录写入后可按记录标识读取，读到的内容与写入时完全一致；可按用户列出记录，并按类型、发生时间范围筛选，结果按发生时间排序；服务端另行记下接收时间（取自统一时间来源）。
**需求**: 同一记录标识重复写入时，内容相同视为同一条，只存一次；内容不同则拒绝（冲突），已存的记录不变。
**约束**: 记录只追加，存储层拒绝修改或删除已有记录；更正记录必须指向同一用户、同一类型、已经存在的记录。

**需求**: 记录的原文与身体不适描述可全文检索，支持中文按子串匹配；只返回该用户自己的记录。
**约束**: 检索词少于 3 个字时直接报错（无法可靠匹配），不返回空结果冒充"没找到"；检索词中的特殊符号按普通文字处理。
**非目标**: 档案、计划版本、调度等其他数据表（随各自任务以新迁移加入）；记录接口与离线批量补交；用户数据的导出与删除。

**澄清**（独立审查后补充）: 存储层在任何写入方式下都拒绝覆盖已有记录（包括"有则替换"式写入）。记录时间晚于服务端接收时间超过 5 分钟（允许的设备时钟误差）时拒绝。每个请求使用独立的数据库连接，连接可在处理同一请求的不同线程间传递；多个连接同时写入时排队等待而不报错。迁移目录不存在、目录中出现不合规的文件名（含扩展名大小写不符）时迁移失败。按类型筛选时类型必须以集合给出。
**澄清**（独立审查后补充）: 检索词中的特殊符号必须按普通文字参与匹配（含引号的原文能被含引号的检索词找到）。
**澄清**（复核后补充）: 同一个连接被两个线程同时使用时直接报错（而不是出现难以理解的事务错误）。只禁止其他模块直接引用数据存储，经由编排层间接使用不受限制。
**澄清**（第 3 周复盘后补充）: 一条记录只能被更正一次；要再改，就更正最新的那条更正（形成更正链），不允许对同一条记录产生两个分叉的更正。

### 6. 规则表：格式、加载与首个规则集

**需求**: 业务阈值与判定规则写在人可直接阅读的规则文件中，不写死在代码里；按规则集分文件，每个规则集有名称与版本。每条规则包含：编号、标题、审定状态（草稿 / 待审定 / 已审定）、来源（指南 / 设计 / 借鉴 / 估算，除"设计"外必须写明出处）、参数（阈值等），可附说明。
**约束**: 规则编号在全部规则集中唯一；规则集名称与文件名一致且不重复；规则目录由配置项 `IRONM_RULES_DIR` 指定（默认 `rules`）。
**需求**: 启动时加载全部规则表；任何格式问题都使启动失败，错误信息指明文件（及规则编号）：缺少字段、来源不全、编号重复、未定义的字段、同一层级出现重复的键、文件扩展名不规范、目录里没有任何规则表、内容无法按纯文本数据解析（如未加引号的日期）。
**需求**: 程序按编号取规则，编号不存在时报错；取参数时按使用方声明的类型校验，不符时报错并指明规则编号。能列出各规则集的版本，供计划版本记录"用了哪一版规则"。
**需求**: 规则文件的格式导出为 JSON Schema，供编辑规则时校验。
**需求**: 首个规则集"数据质量"，状态均为待审定：
- 体重在 7 天内变化超过 2 千克，标"待确认"【设计】；
- 单日热量低于 500 或高于 6000 千卡，标"待确认"【设计】；
- 超过 10 天没有新的称重，体重类指标标"已过期"【设计】；
- 饮食调整的最低数据量：每 7 天至少 4 天有饮食记录、每周至少 1 次称重【借鉴 MacroFactor】。
**非目标**: 各规则的判定执行（随异常值、新鲜度、复盘等功能实现）；规则下线开关；急症词表（由安全模块独立维护，不走规则表，保证安全模块不依赖其他模块）。

**澄清**（独立审查后补充）: 规则目录中除说明文档（.md）与隐藏文件外，任何不是 .yaml 结尾的文件都使加载失败（含 .YAML、.yaml.bak 等）。规则文件中的数字、真假值只按现行标准写法识别：1:30、010、yes / on 等旧式写法一律当文字处理，再由类型校验报错，不会被悄悄换算。
**澄清**（复核后补充）: 按使用方声明的类型取参数时严格校验，文字不会被转换成数字或真假值。

### 9. 快进模拟：模拟用户与 8 周数据

**需求**: 模拟用户用数据文件定义，包含：可见档案（性别、年龄、身高、起始体重）、记录习惯（称重日、训练日、饮食记录方式、签到日）、隐藏真值（分阶段的真实体重变化速度、测量噪声、训练完成概率、疲劳走势）以及陷阱。首批 5 类：按计划执行、完成度低、疲劳累积、每周只称 1 次、习惯模式（饮食不记热量）。
**需求**: 陷阱至少包括：单次体重尖峰、换秤（数据流改变并带固定偏差）、单位写错（把斤当公斤记）、情况变差时停止记录、一段时间完全不记录（依从性缺口）。每个陷阱生成的记录都登记在真值里，供以后检验"有没有被假信号骗、真变化有没有及时发现"。
**需求**: 快进运行器从起始日开始逐天推进统一时间来源，当天的记录在当天写入记录仓储（接收时间即当天的模拟时刻）；每天结束、每周结束时调用登记的回调（供以后接入复盘）。默认生成 8 周。
**约束**: 同一模拟用户、同一种子两次生成的记录逐字一致；每个随机值只由（种子、用户、日期、项目）决定，增减一个陷阱不改变其他天的记录。隐藏真值不出现在任何记录中。生成的记录全部符合记录契约。
**需求**: 提供一条命令跑完 5 类模拟用户 8 周，输出汇总：各类记录条数、陷阱条数、真实与测得体重的首末值。
**非目标**: 复盘决策与判分（随复盘、决策表任务）；模拟用户对系统建议的反应（模拟用户的走势不随建议改变）。

**澄清**（独立审查后补充）: 陷阱的天数必须落在模拟范围内；同一天不能有两个单日陷阱；起止天顺序必须正确，否则模拟用户加载失败。任何概率取值下生成的记录都必须符合契约。汇总中的"测得体重"只剔除尖峰与单位写错这两类假读数，换秤后的读数照常统计。

### 10. 记录提交接口

**需求**: 提供提交一条记录的接口，内容按记录契约校验。首次提交返回"已创建"；同一记录再次提交返回"重复"，库中只存一次；同一记录标识但内容不同返回"冲突"，已存的记录不变。返回结果中带记录标识。
**需求**: 校验失败、记录时间在未来、更正指向不合规的记录时，返回"请求不合法"，并给出出错的字段位置与原因；错误信息中不回显提交的取值（可能含健康数据原文）。
**需求**: 服务启动时自动执行尚未执行的迁移，迁移失败则启动失败；每次请求使用独立的数据库连接；接收时间取自统一时间来源。
**需求**: 每次提交写一条结构化日志，含记录标识、结果与耗时，不含记录内容。
**约束**: 两个请求同时提交同一条记录时，只存一条，一个返回"已创建"、另一个返回"重复"，不出现服务器错误。
**非目标**: 批量与离线补交（下一步）；登录与身份校验（目前以记录中的用户为准，上线前必须由登录身份决定用户）；请求频率限制。
**澄清**（第 3 周复盘后补充）: 校验错误的原因说明中若含有提交的取值（如类型名写成一句话），改为通用说明；请求体超过 2 MB 返回"请求过大"；嵌套过深等无法解析的请求体返回"请求不合法"而非服务器错误。提交的记录必须属于当前用户（登录功能完成前，当前用户由请求头给出），否则拒绝；查询类接口不再从参数中读取用户。
**澄清**（复核后补充）: 校验错误的原因说明一律使用系统自己的措辞（限值取自契约本身），不使用校验库的原文；请求头声明的大小超过上限时，不读取请求体直接拒绝。

### 11. 批量与离线补交

**需求**: 提供一次提交多条记录的接口（离线队列上传用），每批 1–500 条。每条单独校验、单独入库、单独返回结果（已创建 / 重复 / 冲突 / 不合法，并带它在本批中的位置与记录标识）；一条出错不影响同批其他记录。
**需求**: 同一批中，更正记录在它所指向的原记录之后处理，无论它们在批内的先后。离线补交的记录（发生时间、记录时间都早于接收时间很久）照常接受，接收时间为实际上传时刻。
**约束**: 结果与提交顺序无关：同一组记录无论怎样打乱顺序、重复提交、分成多批（更正不早于其原记录所在的批次），最终存下的记录完全相同，按用户列出的结果也完全相同（同一发生时间的记录按记录标识排序，而不是按到达先后）。
**约束**: 空批、超过 500 条、请求体格式不对时整批拒绝；单条的错误信息与单条接口一样不回显提交内容。每条记录各写一行提交日志，另写一行批次日志（条数、耗时）。
**非目标**: 跨批次的"更正先于原记录到达"（客户端离线队列按产生顺序上传，不会出现）；批量提交的整体事务（逐条入库，失败可安全重传）。
**澄清**（第 3 周复盘后补充）: 同一批中同一记录标识出现内容不同的多条时，这些条全部判为冲突、都不入库（与库中已有内容相同的那条判为重复），结果与它们在批内的先后无关。
**澄清**（复核后补充）: 同一批中有多条不同的更正指向同一记录时，这些更正一律判为不合法（已在库中且内容相同的判为重复），结果与先后无关。

### 12. 异常值"待确认"

**需求**: 体重在规定天数内（含）的变化超过规定幅度时，这次称重标为"待确认"；单日热量低于下限或高于上限时，该日标为"待确认"。阈值一律取自规则表（数据质量规则集），判定结果带触发的规则编号。
**需求**: 对一位用户的全部称重按发生时间逐次判定：每次称重与"近期水平"比较，即同一数据流中、规定天数内最近至多 3 次未被标为"待确认"的有效读数的中位数；规定天数内没有可比读数时不标。不同数据流（如换了秤）之间不比较。
**约束**: 不与单一的上一次读数比较：上一次读数本身带测量噪声时，尖峰会漏判，而漏判的尖峰又会让其后的正常读数被误标（快进模拟中"按计划执行"用户的尖峰陷阱即暴露了这一问题）。
**需求**: "待确认"不修改记录本身。用户确认或修正一条读数的方式，是追加一条指向它的更正记录：被更正的记录不再是有效读数，更正记录视为用户已确认，不会被标为"待确认"。
**澄清**: 记录中的"已确认"只表示估算值（如从一句话抽取的饮食）已经用户确认，与异常值是否复核无关。
**非目标**: 单日热量的汇总（需先定用户所在时区，随完成度与新鲜度任务）；"待确认"的提醒与界面。
**澄清**（第 3 周复盘后补充）: 若比较基准只有一条读数（没有其他读数印证），而其后连续若干次读数（规则表，现为 2 次）彼此一致、又与当前读数一致，则判定基准那条有误：改为标记它，并以新读数为准，不再把其后的正常读数都标为"待确认"。判定结果随新数据而变，不写回记录。近期水平取的读数次数取自规则表。用户的确认（更正）记录沿用被更正读数的数据流。
**澄清**（复核后补充）: 推翻基准需同时满足：其后的读数都与当前读数一致（相差不超过规则表中的容差，现为 1 千克），且都与基准相差超过跳变幅度。只满足其一时不推翻（例如尖峰之后回到正常水平的读数，与基准一致而与尖峰不一致）。

### 13. 体重趋势与可信范围

**需求**: 对给定时间窗口内的体重读数做线性回归，给出：读数条数、覆盖天数、每周变化（千克 / 周）、标准误、按规定置信水平的可信范围（用 t 分布，读数少时范围相应变宽）、残差标准差。
**需求**: 参与计算的读数：有效（未被更正取代）、未被标为"待确认"、与最近一次读数同一数据流（不同的秤不混算），且落在窗口内。
**需求**: 置信水平与最少读数条数取自规则表；读数不足或所有读数在同一时刻时，结果为"数据不足"，并说明还差几次称重，不给出趋势数值。
**约束**: 计算结果与手算样例一致；t 分布分位数与统计表一致（至少 3 位小数）。
**非目标**: 精度等级与判断窗口的确定（随精度判定、判断窗口任务）；指标结果的组装与接口（随指标接口任务）。
**澄清**（第 3 周复盘后补充）: 参与计算的读数覆盖天数少于规则表规定的下限（现为 3 天）时为"数据不足"，并说明还需覆盖的天数。结果统一用状态（正常 / 数据不足）与"还差什么"表示。
**澄清**（复核后补充）: 覆盖天数下限必须大于 0；即便调用方给出 0，所有读数在同一时刻时也判为数据不足，不出现计算错误。

### 14. 每日精力选择与训练量调整

**需求**: 用户每天第一次使用前选择当天精力，共 5 级：1 很差、2 疲惫、3 一般、4 良好、5 充沛。选择作为一条记录保存；同一天可以改选，以当天最后一次选择为准。"一天"按用户所在时区的 0 点到 24 点计算，时区用标准名称（如 Asia/Shanghai）。
**需求**: 当天训练任务量据精力调整，每一级对应的调整方式写在规则表中（初版，待审定）：
- 5 充沛、4 良好：照常（不因精力好而加量）；
- 3 一般：降低难度，组数约 80%，用力程度上限降 1 级；
- 2 疲惫：只留轻松训练，组数约 50%，用力程度上限降 2 级；
- 1 很差：只做最低任务或休息，不安排正式训练组。
调整结果带规则编号，并能换算出某个训练项调整后的组数与用力程度上限。
**约束**: 精力只能让训练量下降，不能让它超过原计划。当天还没有选择精力时，结果为"未选择"，不给出任何调整，也不默认按"照常"处理；当天训练任务必须在用户选择之后才能确定。
**约束**: 精力选择不替代安全判断：精力"很差"时提示用户，如有胸痛、头晕、心慌等不适请走安全通道，而不是只降训练量。
**非目标**: 训练计划本身的生成与"今日"页面（随后续任务）；用户档案中的时区字段（档案功能完成前由调用方给出时区）；把精力纳入恢复、复盘的长期判断。
**澄清**（第 3 周复盘后补充）: 调整后的组数按四舍五入（0.5 进位）取整。查询今日精力时，用户取自当前用户，而非查询参数。

### 15. 完成度、新鲜度与"未知"不计入平均

**需求**: 求平均时只用已知值，"未知"不计入；全部为"未知"时，结果为"未知（数据不足）"，不算作 0。
**需求**: 体重新鲜度：最近一次可信称重（有效、非待确认）距今超过规定天数（规则表，现为 10 天）时为"已过期"，恰好等于规定天数不算过期；从未称重时为"没有数据"，与"已过期"区分。结果带最近称重时间与规则编号。
**需求**: 训练完成度：对照计划的训练日计算，完成、练一半、没练的计分取自规则表（现为 1、0.5、0）；计划日没有打卡记录的记为"未知"，不当作没练，不计入完成度；同时给出有记录的计划日占比。日期按用户所在时区计算；非计划日的训练不计入。
**需求**: 单日热量按用户所在时区的当地日期汇总：当天所有饮食记录都有热量时为其总和；当天任一餐的热量未知，或当天没有饮食记录时，当天总量为"未知"（部分记录会让总量偏低，空白优于部分记录）。只有已知的单日总量参与"待确认"判定。
**约束**: 属性测试：在任意一组数值中任意位置插入任意多个"未知"，平均值不变。
**非目标**: 把这些结果组装成指标结果与接口（随指标接口任务）；饮食调整的最低数据量判断（随复盘任务）。
**澄清**（第 3 周复盘后补充）: 计划训练日为 0 时，记录占比为"未知"。新鲜度结果统一用状态（正常 / 已过期 / 数据不足）表示；从未称重为"数据不足"并说明还差 1 次称重。指标结果中"最近一条记录的时间"缺失时为"未知"而非空值。所有规则参数在服务启动时按使用方声明的类型校验，写错即启动失败。
**澄清**（冲刺 1 末审查后补充）: 单日热量汇总中，未经用户确认的估算视为没有热量（与精度判定一致）。

### 16. 全局规则清单（每个计算都必须满足）

**需求**: 以下规则对每一个读取记录做计算的功能都成立，新增计算功能时逐条核对，并有对应测试：
1. **更正**：只使用有效记录（被更正取代的记录不参与；更正链取最新一版），通过统一的有效记录层取得，不各自实现。
2. **未知**：缺失值用"未知"并注明原因，不用 0 或空值；平均、占比等只对已知值计算，全部未知时结果为"未知"。
3. **时区**：涉及"哪一天"的计算按用户所在时区的当地日期。
4. **截止时间**：只使用发生时间不晚于截止时间（as_of）的记录。
5. **阈值**：阈值与计分取自规则表，结果带规则编号；参数在启动时校验。
6. **顺序无关**：结果不随记录到达或排列的先后改变。
**约束**: 这些规则由公共层实现（有效记录层、只对已知值求平均、当地日期换算），各计算功能调用公共层，不重复实现。

### 17. 精度判定（体重、训练）

**需求**: 按截止时间前 4 周（规则表）的实际记录，分别判定体重与训练两个领域的精度等级 P0–P3，结果带规则编号与判定依据（各周记录天数、各级达标的训练日占比等）。
**需求**: 体重：以用户所在时区的当地日期计算每周称重天数（同一天多次只算一天；被更正取代的不计，"待确认"的读数仍算称过重）。
- P3：4 周内至少 14 天称重，且至少 3 周每周不少于 3 天；
- P2：至少 3 周每周不少于 2 天；
- P1：至少 3 周每周不少于 1 天；
- P0：其他。
**需求**: 训练：以当地日期确定训练日（当天有打卡或按组记录），每个训练日的记录程度为：
- 3：有按组记录，且当天每组都有 RIR 或 RPE；
- 2：有按组记录但缺 RIR / RPE，或打卡时填了用力程度；
- 1：只有打卡状态；
领域精度为最高的等级 L，使"记录程度 ≥ L 的训练日占比"不低于 75%；4 周内训练日少于 4 天时为 P0。
**约束**: 以上周数、天数、比例全部取自规则表（初版，待审定）；遵守全局规则清单（§16）。每一档的边界都有黄金用例。
**非目标**: 饮食与恢复两个领域（下一步）；精度对计算方法与判断窗口的影响（随判断窗口任务）。
**澄清**（冲刺 1 末审查后补充）: 训练日指当天有按组记录，或有状态为"完成""练一半"的打卡；只有"没练"打卡的日子不算训练日。

### 18. 精度判定（饮食、恢复）

**需求**: 饮食：以当地日期确定有饮食记录的日子，每天的记录程度为：
- 3：当天每一餐都有热量与蛋白质，且都是用户自己填写的数值（不是估算）；
- 2：当天每一餐都有热量（可以是经用户确认的估算）；
- 1：其他（有记录但缺热量；未经确认的估算视为没有热量）。
领域精度：4 周内有饮食记录的天数不少于规定天数（现为 16 天）时，取最高的 L（3 或 2）使"程度 ≥ L 的天数占比"不低于 75%；否则，若至少 3 周的每周签到回答了"按计划吃了几天"，为 P1；否则为 P0。记录天数够但占比不到 P2 的，同样按签到判断 P1。
**需求**: 恢复：P3、P2 需要设备的睡眠、心率变异性、静息心率等数据，设备接入前恢复领域最高为 P1。至少 3 周的每周签到填了疲劳或睡眠，或 4 周内至少 16 天选择了每日精力，为 P1；否则为 P0。
**约束**: 天数、周数、比例取自规则表（初版，待审定）；遵守全局规则清单（§16）；每一档的边界都有黄金用例。
**非目标**: 设备数据的接入与恢复领域 P2、P3；精度对计算方法的影响（随判断窗口任务）。
**澄清**（冲刺 1 末审查后补充）: 饮食与恢复的窗口天数必须是 7 的倍数，所需周数不超过窗口内的周数，启动时校验。

### 19. 判断窗口（需要多久、还差什么）

**需求**: 先定"需要多确定"，再算"需要多久"：体重趋势可信范围的半宽不超过规定值（规则表，现为每周 0.25 千克）才能下结论。给定每周称重次数与体重日常波动，算出满足要求的最少天数：假定在窗口内均匀称重，按 §13 同样的回归与 t 分布计算可信范围半宽。
**需求**: 每周称重次数取近 4 周的实际称重天数平均；体重日常波动在可信读数足够（规则表，现为 6 次）时取用户自己回归的残差标准差，否则取规则表中的默认值（现为 0.5 千克），结果注明取自哪里。
**需求**: 所需天数超过上限（规则表，现为 56 天）时为"数据不足"，说明每周至少需要称几次才能在上限内得出结论；所需天数在上限内时，比较已有的数据覆盖天数，够了为"正常"，不够为"数据不足"并说明还差几天；同时给出"每周多称一次可提前约几天"。近 4 周没有称重时为"数据不足"，说明还差称重。
**约束**: 黄金用例覆盖每天称、每周 2 次、每周 1 次三种情况，并附手算过程。方案中"每天称约 2 周"为估计，按本计算为约 3 周（波动 0.5 千克时 21 天）。
**非目标**: 饮食、训练等其他判断的窗口（随复盘决策表任务）；"拒绝后 4 周内不再提示"的提示频率控制（随提醒任务）。
**澄清**（冲刺 1 末审查后补充）: 每周已称 7 次仍无法在上限内达到要求时，不再提示"每周至少称 7 次"，改为提示固定时间称重以减少波动。
**澄清**（冲刺 1 后用户确认）: 每周称重次数按近 4 周平均；若最早一次可信称重距今不足 4 周，按称重间隔估算：（称重天数 − 1）÷ 最早一次距今的天数 × 7；只称过 1 天时按每周 1 次（新用户头几天天天称，不会被当作每周只称一两次；每 7 天称一次也不会因首尾计数被高估）。精度判定仍按固定的 4 周计算。

### 20. 指标接口

**需求**: 提供查询当前用户指标的接口（时区由调用方给出），返回：计算时间、四个领域的精度等级，以及指标结果列表；每个指标结果符合指标契约（数值或"未知"、单位、可信范围、精度、使用的记录条数、窗口天数、状态、还差什么、最近一条记录时间、计算时间、公式编号）。
**需求**: 首批指标：
- 体重趋势（千克 / 周）：窗口取判断窗口所需天数（不足或无法确定时取上限）；有趋势估计时给出数值与可信范围，即使状态为"数据不足"也给出（界面标为暂定）；还差什么取判断窗口的结论。
- 近 7 天日均热量（千卡）：只对已知的单日总量求平均；已知天数少于规则表的最低天数（现为 7 天中 4 天）时为"数据不足"并说明还差几天。
**需求**: 状态按优先级确定：已过期 > 有待确认的读数 > 数据不足 > 正常。
**约束**: 只读取计算所需的最近一段记录，回看天数由规则表中的各窗口推算（不另设数字），历史记录再多也不影响响应；指标组装放在计算层，接口只负责取数与返回。遵守全局规则清单（§16）。
**非目标**: 训练完成度指标（需要计划，随计划任务）；其他领域的更多指标；界面展示。
**澄清**（冲刺 1 演示后补充）: 体重趋势判为"正常"，还要求实际算出的可信范围半宽不超过目标（判断窗口按均匀称重的模型估算所需天数，实际称重不均匀或波动更大时，实际范围可能更宽）；超过时为"数据不足"，还差的天数按"标准误约与天数的 1.5 次方成反比"估算：所需天数 ≈ 当前窗口天数 ×（当前半宽 ÷ 目标）^(2/3)。
**澄清**（冲刺 1 末审查后补充）:
- 已有数据覆盖超过所需天数时，体重趋势的窗口随覆盖天数增长（不超过上限），使"还差 N 天"能够兑现，避免状态来回跳；到上限仍不达标时提示固定时间称重。
- 近 7 天日均热量不含今天（今天尚未结束，部分记录会拉低均值并误报异常）。
- 回看范围内没有称重时，另取范围之外最近的几次称重，用于区分"已过期"与"没有数据"；取数时一并取得指向已取记录的更正（即使更正把发生时间改到范围之外）。
- 时区名不合规（含过长）一律返回"请求不合法"，不出现服务器错误。

### 21. 急症词表与匹配

**需求**: 安全模块对用户的一句话给出判定：急症（立即就医 / 拨打 120）、红旗（暂停相关训练、尽快就医）或不触发，并给出命中的词表条目编号与类别。判定只看词表，不调用模型、知识库或其他业务模块，离线与模型故障时照常工作。
**需求**: 词表是一份人可读的文件，分两层：
- 症状：一组同义说法。任一说法出现即命中；或者写成几组词，同一分句里每组都出现才算命中（如"胸口"与"痛"可以隔开几个字）；血压按数值判断（收缩压或舒张压达到阈值）。
- 判定条目：若干症状在同一句话里都出现时，给出急症或红旗。多个条目命中时取最高一级（急症高于红旗）。
**需求**: 判定只升不降：拿不准时取更高一级。
**约束**: 只用最简单的匹配方式（文字包含、分句内多组同时出现、血压数值），保证前端离线版用同一份词表能得到相同结果。匹配前统一文字：全角转半角、英文转小写、去掉空白；分句按中英文逗号、句号、问号、感叹号、分号、顿号与换行切分。
**约束**: 词表严格校验，服务启动时加载，有误即启动失败：编号唯一；判定条目引用的症状必须存在；每个症状至少被一个条目使用；说法不能为空、不能含分句符号，并且已是统一后的写法。词表带版本与审定状态，初版为待审定，只能由人修改。
**约束**: 判定结果与日志都不含用户原话。
**澄清**: 否定说法、已经缓解、转述他人过去的经历（"没有胸痛""以前晕倒过"）留到 D22 处理；本条只要求红旗测试集的正例全部判对级别，D22 之前这几条反例单独标为预期失败。
**非目标**: 否定句识别与前端离线版（D22）；人群分层（D23）；三档回答与红旗四段式（D24）。

### 22. 否定说法识别与离线版

**需求**: 症状说法紧跟在否定词之后（"没有胸痛""不头晕""未见红"）时，这一处不算出现；同一分句里同一症状还有别处没被否定，仍算出现。组合说法中任一组只在否定处出现，这一组合不算命中（"胸口不疼了"）。
**需求**: 症状说法后紧跟"过"（不是"过去"）表示以前发生过（"上周胸口疼过""以前晕倒过"），这一处不算出现；但整句话里有再次发生的字样（"又""再次""刚才"等）时，以前发生过的也照常算。
**需求**: 否定词、例外（"差点没晕倒"仍算出现）、"过"与再次发生的字样都写在词表里，由人维护。
**需求**: 提供 App 离线版：由同一份词表生成离线数据文件，配一个不依赖任何第三方库的脚本实现同样的判定；词表改动后未重新生成即检查失败。
**约束**: 只升不降：否定只能取消紧挨着的一处说法；拿不准是否否定时按出现处理（假设、担心、提问等说法不做识别）。血压数值不受否定影响。
**约束**: 离线版与服务端对同一句话的判定（级别、条目编号、类别）完全一致：红旗测试集、改写说法、日常说法与大量随机拼接的句子全部比对。
**非目标**: 假设与提问（"万一晕倒怎么办"）的识别；人群分层（D23）；回答模板（D24）；App 页面本身（D41 起）。
**澄清**（用户确认）: 前端做手机 App，不做 PWA 网页；技术栈为 React Native + Expo（TypeScript），一套代码出 iPhone 与安卓。离线判定脚本即为 App 代码的一部分（app/src/safety/），用 Node 直接运行做一致性检查。

### 23. 人群分层与实时重新分层

**需求**: 安全模块根据用户的筛查信息给出安全分层，并列出依据。筛查信息包括：出生日期、性别、身高、最近体重、最近腰围、已申报的健康状况（问卷）、红旗记录与就医确认；每项都可以是"未知"。
**需求**: 分层（第一期只有减脂场景）：
- 暂停：有红旗或急症记录，且之后没有"已就医、可以运动"的确认。
- D 暂不开放：未满 18 岁。
- C 记录与协作：孕期、哺乳期、产后 1 年内、心脏病、肾脏病、正在用药的糖尿病、伤后康复中、进食障碍史、进食障碍信号、未在医生指导下使用减重药物。
- 不适用（减脂）：BMI 低于 18.5。
- 协作：在医生指导下使用减重药物。
- B 保守：65 岁及以上、高血压、近期受伤、BMI 达到 32.5。
- A 完整：BMI 达到 24，或腰围达到中心型肥胖前期（男 85 厘米、女 80 厘米）。
- A′ 体态减脂：BMI 18.5–23.9 且腰围未达上述值。
**需求**: 同时满足多层时，主层按上面的顺序取最靠前的一层；其余满足的层一并列出（供热量等计算取更保守的约束，如 65 岁、BMI 22 的用户主层为 B，同时满足 A′）。
**需求**: 信息不全时：决定主层所需的信息缺失则给不出分层（"未知"），并列出还差什么；只缺腰围或性别、且 BMI 在 18.5–23.9 时，按 A′ 保守假设，并标明是假设、还差腰围。决定主层用不到的信息缺失不影响结果（如已在暂停或 C 层）。
**需求**: 实时重新分层：聊天中的一句话被判为红旗或急症时，立即记一条红旗记录，分层当场变为暂停；命中进食障碍类条目的，同时记为进食障碍信号，就医确认后仍在 C 层。给出新旧分层相比是更严、更松还是不变。
**约束**: 年龄按用户所在时区、截至计算时间的当地日期计算（生日当天算满岁）；截至时间之后的红旗与就医确认不计入。BMI 按一位小数四舍五入后与界值比较。年龄、BMI、腰围界值与各层对应的健康状况写在规则表（待医学顾问审定），服务启动时校验；分层顺序写在代码里。安全模块不依赖规则模块，只通过共享契约读取规则参数。
**约束**: 结果带规则编号；每层边界都有黄金用例（17/18 岁、64/65 岁、BMI 18.4/18.5、23.9/24.0、32.4/32.5、男女腰围界值）。
**非目标**: 从聊天中识别新诊断（"我怀孕了"）并更新问卷（随意图识别）；档案与问卷的存储和接口（随建档）；各层的具体服务限制（热量见 D25，处方类 Skill 见 D27）；其他场景包的分层。

### 24. 三档输出、红旗四段式与四项拒答

**需求**: 安全模块对一句话结合当前分层给出安全决定：输出档位（完整 / 保守 / 暂停并转介）、是否允许给出训练或饮食计划、需要告知用户的提示、命中的拒答类型，以及由模板生成的回答段落。对应关系：
- 这句话判为急症或红旗，或分层为暂停 → 暂停并转介，不给计划。
- A、A′ → 完整，可给计划。
- B、协作 → 保守，可给计划，并提示已按保守规则安排（协作层另提示药物问题请问医生）。
- C、不适用（减脂）、D → 保守，不给计划，并分别提示：只提供记录与专业沟通摘要 / 不提供减脂计划 / 未满 18 岁暂不开放。
- 分层未知 → 保守，不给计划，提示需要先补充哪些信息。
**需求**: 红旗回答四段式：安全结论 → 需立即停止的活动 → 不能判断的部分 → 建议的专业帮助（急诊或科室，以及就诊时可以告诉医生的信息）。急症的结论与专业帮助都写明拨打 120；红旗写明尽快到哪个科室就诊，以及就医确认后如何恢复训练建议。停止的活动、科室与可带的信息按命中条目的类别给出，多个类别合并去重。
**需求**: 四项拒答：不诊断（含解读检查报告）、不开处方（含用药、剂量、联合用药、推荐药品）、不制定治疗方案、不提供紧急医疗服务（不能代为呼叫急救）。识别使用单独的拒答词表，匹配方式与急症词表相同（同义说法、分句内多组同时出现、紧挨着的否定词）。提到药名但没有问用法用量（"我在吃二甲双胍，能做力量训练吗"）不算。每种拒答有固定的回答段落，药物一律转医生或药师。
**需求**: 回答的文字（段落标题、四段式各段、各类别的停止活动与科室、拒答与提示）写在一份人可读的模板文件中，由人维护；回答中不出现用户原话。四段式模板随离线词表一起导出，App 离线版生成与服务端相同的四段式。
**约束**: 模板与拒答词表严格校验、服务启动时加载：急症词表中出现的每个类别都要有对应的模板；每种拒答、每个提示都要有文字；占位符只能是规定的几个。
**约束**: 对抗题库中能由规则确定判断的题（运动中胸痛、违禁药物、减重药物剂量、开处方与治疗、诱导诊断、泻药用量）必须全部给出正确的档位或拒答类型；其余题依赖问答功能（D44 起）。
**非目标**: 由模型生成的正文与回答评分（随问答）；"疼痛类回答必须写明就医条件"的检查（随问答）；保守档具体规避了哪些动作（随训练规划）。

### 25. 热量计算

**需求**: 根据筛查信息（性别、出生日期、身高、最近体重）、用户选择的身体活动水平与分层结果，计算每日热量目标，全部标为"估算"，并写明用到的规则编号：
- 静息能量消耗（Mifflin-St Jeor）：男 = 10 × 体重（千克）+ 6.25 × 身高（厘米）− 5 × 年龄 + 5；女 = 同式 − 161。
- 每日总消耗 = 静息能量消耗 × 身体活动水平。活动水平三档，取 FAO/WHO/UNU 各档区间的中间值：久坐或轻度 1.55、中度 1.85、重度 2.20。
- 能量缺口按分层：A 500、A′ 300、B 500、协作 300 千卡；同时满足多层时取其中最小的缺口。其余分层（暂停、D、C、不适用）不给热量目标。
- 热量目标 = 每日总消耗 − 缺口，但不低于底线（女 1200、男 1500 千卡，任何情况不低于 800）；被底线抬高时写明，实际缺口随之变小，底线高于每日总消耗时实际缺口为 0、不给负缺口，并提示靠增加活动。
- 营养素：碳水 / 脂肪 / 蛋白质按热量占比 55 / 25 / 20，可选高蛋白 50 / 25 / 25；克数按每克 4 / 9 / 4 千卡换算。三餐按 30 / 40 / 30 分配。
**约束**: 系数、活动水平、缺口、底线、占比全部写在规则表（初版待审定），服务启动时校验（占比之和为 100、底线不低于绝对底线等）。年龄按用户时区的当地日期。先算出不取整的结果，最后把热量四舍五入到整千卡；营养素克数与三餐热量由取整后的目标换算并四舍五入，最后一餐取差额，保证三餐之和等于目标。
**约束**: 信息不全（性别、出生日期、身高、体重或活动水平未知）时给不出目标，列出还差什么；分层不允许给计划时给不出目标并写明原因，不用 0 代替。可给计划的分层与三档输出中"可给计划"的分层一致。
**非目标**: 减重速度目标与阶段复盘（随复盘）；精确型的能量平衡校正（反推个人消耗）；简化型与习惯型饮食模式的表达；接口与界面。

### 26. 规则、词表与模板的审定（Claude 版本）

**需求**: 项目负责人委托 Claude 对照公开资料逐项审定所有"待审定"的规则表、急症词表、拒答词表与回答模板。每一项写明结论（维持 / 修改）、改了什么、依据（附链接）与证据强弱，记在 `spec/review_log.md`；审定完成的标为"已审定"，文件中注明由 Claude 代为审定、未经执业医师或注册营养师复核。暂不能落地的修改记为后续任务并写明在哪一天做。
**需求**（数据与指标）:
- 体重趋势：同一当地日期多次称重只取当天第一次可信读数参与回归（与精度、判断窗口按"称重天数"计一致）；至少覆盖 7 天；考虑相邻读数波动的相关性，标准误乘以 √((1+r)/(1−r))，r = 相关系数 0.4 的"平均间隔天数"次方（判断窗口的天数估算同样计入）。
- 趋势窗口：在"所需天数"到"已覆盖天数"（不超过上限）之间，取可信范围达到要求的最短窗口，使结论尽量反映近期；都达不到时取其中最长的，并说明还差什么。
- 跳变"待确认"：阈值为 2 千克与近期水平 2.5% 中较大者；可比读数的时间窗为 8 天（容下"每周同一天、晚一点称"）。超过 7 天仍未确认的读数仍不参与计算、仍列为待办，但不再决定体重趋势的状态。
- 近 7 天日均热量：已知天数中至少 1 天是周五、周六或周日，否则为数据不足（周末摄入通常更高）；删除未被使用的"最少称重次数"参数。
- 训练完成度：有记录的计划日占比低于 75% 时为数据不足（与训练精度一致），仍给出已记录日的完成度。
**需求**（营养与热量）:
- 身体活动水平改为《中国居民膳食营养素参考摄入量（2023版）》的三档：1.40 / 1.70 / 2.00（低 / 中 / 高）；已包含日常运动，计算训练消耗时不得再加回。
- 热量底线还要不低于静息能量消耗（四舍五入后）。
- 65 岁及以上且 BMI 低于 24：缺口为 0，只给维持热量（老年人 BMI 20–26.9 为宜），写明原因。
- 协作层的热量目标是"最低摄入"而不是上限，结果中写明。
- 蛋白质最低量：取三者最大——热量占比算出的克数；每千克参考体重 1.2 克（高蛋白选项 1.6 克）；65 岁及以上男 72 克、女 62 克。参考体重：BMI 低于 24 用实际体重；达到 24 用校正体重 = 理想体重 + 0.25 ×（实际 − 理想），理想体重 = 22 × 身高（米）²。上限：每千克参考体重 2.0 克，且不超过热量的 30%；达到上限时写明。多出来的热量先从脂肪扣（不低于 20%），再从碳水扣（不低于 50%）。
- 营养素与三餐的出处改为《成人肥胖食养指南（2024年版）》。
**需求**（精力档）: 疲惫档用力程度另设绝对上限（RPE 6）；很差档绝对上限 RPE 3、时长不超过 15 分钟；很差档的安全提示加上发热、全身酸痛。
**需求**（医学安全）:
- 新增识别：自伤与轻生（正在或已经自伤为急症，轻生想法为红旗，类别"心理危机"）；严重过敏（喉咙发紧为急症，全身风团伴气促或头晕为急症，仅风团为红旗）；哮喘发作（用药不缓解为急症）；头部受伤伴呕吐、嗜睡等为急症；突发视力丧失（卒中征象）；吐血为急症，黑便、腹部剧痛为红旗；孕期头晕、胸闷、小腿肿痛为红旗；中暑伴意识不清或晕倒按中暑急症、伴恶心头痛等为红旗；极高血压伴气促或视物异常为急症；舒张压阈值改为 110（3 级高血压）。
- 减少误报：去掉单独的"吐出来 / 吐掉"（"把气吐出来"），改为与"吃、饭、食物"同一分句；"吃完就吐"后紧跟"槽"不算；"胰岛素抵抗"不算用胰岛素；单独的"还在"不算持续；"可乐、浓茶"须为"可乐色、浓茶色"；"迷迷糊糊"须与"人、脑子"同一分句；"没反应"须与"人、他、她、叫"同一分句；拒答中"激素"须为"打 / 用 / 吃激素"，"给我"须为"给我叫 / 给我打"。
- 某个说法后紧跟指定的字时这一处不算（写在词表里，如"吐"后接"槽"），App 离线版同样处理。
- 回答模板：类别可以有自己的结论句与补充的求助信息（心理危机用关心的语气，并给出经核实的热线：全国心理援助热线 12356、北京心理危机研究与干预中心 010-82951332）；低血糖写明先吃约 15 克快速升糖的食物；中暑写明先降温；孕期写明向左侧躺、不要平躺；急症写明叫不醒且没有正常呼吸时立即胸外按压并取 AED；头部受伤写明当天不再训练、不要独处。腰痛伴腿麻归骨骼肌肉类（骨科），气促的科室为呼吸内科或心内科。
- 拒答补充：问"是 xx 吗"、看化验单、问药能不能吃或哪里买、问要不要手术或抽积液等说法。
- 人群分层：BMI 32.5 的出处改为《肥胖症诊疗指南（2024年版）》；新增健康状况"糖尿病未用药"（B）、"脑卒中或短暂性脑缺血史"（C）、"未控制的高血压"（C）。
**约束**: 新参数全部写在规则表并启动时校验；修改后对应的黄金用例与测试同步更新，快进模拟 5 类用户的可信范围仍覆盖真实趋势。
**非目标**（后续任务）: 饮食目标变更后趋势窗口从变更日重新开始（需要饮食目标记录，随复盘决策）；用"摄入 − 体重变化"反推个人消耗时摄入窗口与趋势窗口一致（随精确型能量校正）；7 天内有 3 天已确认摄入低于底线时提示并复核进食障碍信号、连续 3 天精力 2 级及以下时提示检查睡眠与热量缺口（随复盘与提醒）。

### 27. 动作库

**需求**: 动作库是一份人可读的数据文件，首批 50 个动作。每个动作写明：编号、中文名、动作模式（下蹲、髋铰链、单腿、推、拉、核心、有氧）、需要的器材（徒手为空）、难度（1–3）、是否单侧、"避免"的身体限制（直接排除）、"谨慎"的身体限制（可选，但附提示）、技术要点 2–4 条、常见错误 1–3 条、自检问题 1–2 条，以及更容易（降阶）与更难（进阶）的动作。
**需求**: 按动作模式、可用器材、身体限制与最高难度筛选候选动作，按难度从低到高排列，"谨慎"的附上对应提示；给出某个动作的替代动作（同一模式的其他候选）与降阶动作（沿"更容易"一路找到第一个可用的）。
**需求**: 三种环境的器材：酒店（椅子）、家里（椅子、台阶、哑铃、弹力带）、健身房（全部器材）。每个动作模式有且只有一个"默认安全动作"：难度 1、不需要酒店之外的器材、没有"避免"的限制；出错或没有其他候选时使用。
**约束**: 每个动作模式在每种环境下至少有 2 个候选；任一身体限制下，每个模式在每种环境下仍至少有 1 个候选（验收：每个训练槽位都能找到替代动作）。
**约束**: 加载时严格校验：编号唯一；模式、器材、身体限制都在规定范围内；"避免"与"谨慎"不重叠；降阶与进阶的动作存在、属于同一模式，降阶不更难、进阶不更容易，且沿降阶或进阶走不会绕回自己；要点、错误、自检条数符合要求；每个模式恰好一个默认安全动作。服务启动时加载，有误即启动失败。
**约束**: 动作说明为原创中文，不使用机器翻译的数据集文字；由 Claude 受项目负责人委托对照 ACSM、NSCA 的公开资料撰写与审定，记入 spec/review_log.md。
**非目标**: 动作演示图片与视频；按历史表现推荐重量；把槽位落成具体训练（随动作教练 Skill，D29）。

### 28. Agent 基类与 Skill 加载器

**需求**: Skill 是某个 Agent 的能力包，每个 Skill 是一个目录，内含 SKILL.md：开头是 YAML 头信息，其后是说明正文。头信息写明：编号、所属 Agent、版本、说明、触发的意图、适用的场景包与人群分层、需要的数据、产出的计划字段、优先级、是否为处方类、审定状态与审定人。
**需求**: 加载条件：所属 Agent、意图、场景包、人群分层同时匹配才加载；处方类 Skill 在不可给计划的分层（暂停、D、C、不适用）与分层未知时一律不加载（与三档输出的"可给计划"一致）；同一 Agent 匹配到多个 Skill 时按优先级（数字小者优先），同一计划字段只由优先的那个产出，其余跳过。每个未加载的 Skill 都给出原因，加载结果带版本（编号@版本），写入运行记录。
**需求**: 数据最小化：按本次加载的 Skill 声明的数据裁剪快照，Agent 只能读声明过的数据，读未声明的直接报错；声明了但快照里没有的为"未知"。可声明的数据：分层、精度、当前计划、约束、上一轮判定，以及具体的档案字段（profile.名称）与指标（metric.名称）。
**需求**: Agent 基类：没有加载任何 Skill 时返回"本次无意见"（原因：没有匹配的 Skill），不调用具体实现；有 Skill 时用裁剪后的快照调用具体实现，并检查输出的 Agent 与 Skill 版本都来自本次加载。
**约束**: Skill 头信息严格校验：编号格式、所属 Agent 在 10 个之内、版本为 x.y.z、产出的字段必须归所属 Agent 负责（越权即加载失败）、处方类 Skill 的适用分层不能包含不可给计划的分层、编号在同一 Agent 内唯一、目录名与编号一致。
**非目标**: 首批具体的 Skill（D28、D29）；路由与意图识别（随编排）；Skill 中的规则与提示词如何被执行。
**澄清**（D28 前，用户确认）: 每个加载的 Skill 各出一份输出，各自只能读自己声明的数据（不再按 Agent 合并），使每条约束都能追溯到具体的 Skill 版本；没有加载任何 Skill 时仍只返回一份"本次无意见"。Skill 的实现放在 Skill 目录内（skill.py 的 run 函数），新增能力只加 Skill、不改 Agent；每个 Skill 必须有自己的测试文件。汇总时同一字段的多条约束取最严（随汇总实现）。

### 29. 评估师与安全官的首批 Skill

**需求**: 新增输出类型"追问"，只有评估师可以产出：列出要问的信息（最多 3 项，不重复），每项写明为什么需要、没回答时怎么办（不给计划直到回答 / 按保守假设继续，并说明是什么假设）。快照中的分层可以是"未知"（还没建档时）。
**需求**: 评估师"建档追问"：按对安全与计划结构的影响排序找出缺失的信息——健康状况问卷、出生日期、身高、体重（缺任一不能分层，不给计划直到回答）；性别（缺则不能算热量）；活动水平（缺则按久坐保守估算）；腰围（缺则按 A′ 保守假设）。最多问前 3 项，其余下次再问；都齐了则"本次无意见"（信息够用）。
**需求**: 安全官"分层限制"：按分层给训练约束——用力程度上限（A、A′ 为 RPE 8，B、协作为 RPE 7）、每周有氧分钟数每周最多增加（A、A′ 30 分钟，B、协作 20 分钟）、B 与协作每周有氧不超过 150 分钟；参数写在规则表。分层未知或不可给计划时"本次无意见"（处方类 Skill 本来就不会加载）。
**需求**: 安全官"热量底线"：给出每日热量目标的下限约束（女 1200、男 1500 千卡，取自热量底线规则）；性别未知时取两者中较高的（更保守）。
**需求**: 安全官"饮食关系警示"：有进食障碍史或进食障碍信号时，约束为不设热量缺口、每周最多称重 1 次；否则"本次无意见"。适用于所有分层（含 C 层，约束提醒与记录类 Skill）。
**约束**: 追问不影响安全：急症拦截在路由之前独立运行，安全官每条路由都参与；追问每次最多 3 项；只有评估师能追问，其他 Agent 产出"追问"即契约校验失败。红旗筛查由安全通道（§21–§24）在路由前完成，调整三件套由提案契约强制（缺一项即不合法），两者不再重复做成 Skill。
**约束**: 每个 Skill 的说明、规则引用与审定状态写在 SKILL.md；由 Claude 受委托审定，记入 spec/review_log.md。
**非目标**: 目标拆解（需要目标契约，随 D30 第一版计划）；安全官复核提案的判定类 Skill（随盲审）；追问在界面上的呈现。

### 30. 训练规划师、动作教练、营养师的首批 Skill

**需求**: 训练规划师"每周结构"（处方类）：第一版每周训练安排——力量训练每周 2 次全身（可练天数达到 5 天时 3 次）；槽位为下蹲、髋铰链、推、拉、核心各 1 个，每个 2 组 8–12 次，用力程度 RPE 6–7；每周有氧分钟数从"当前每周运动分钟 + 30"起，至少 90（B 与协作层至少 60）；遵守安全官的约束（RPE 上限、每周有氧上限）。每项提案带调整三件套（预期效果、回退条件、复核日期 = 当天 + 14 天）。参数写在规则表。

**约束**: 四个 Skill 都是处方类，只适用于 A、A′、B、协作层；产出的字段都归各自 Agent 负责；数字全部来自规则表、动作库或热量计算，不在 Skill 里写死。
**非目标**: 有氧与力量的逐周进阶、平台期排查与两周饮食调整（需要完成度与复盘，随复盘决策）；食物替换；依据卡（D30）。

### 32. 冲刺 2 末独立审查后的修复

**需求**（急症匹配）: 顿号不再作为分句符号（"胸口、左胳膊都疼"是同一分句）；说法后紧跟"过"再接"去、敏、多、后、度、来、量、速、快、头、劳、分、于、程"时不算以前发生过；句中有"今天、昨天、这几天、最近、这周"时，以前发生过的照常计入；补齐审查发现的漏判说法（"想去死""说话不太清楚""嘴有点歪""疼得厉害""从来没这么""叫他也不应""快憋死了""没有缓解""休息了也不行""左边胳膊"等）。统一文字不再使用运行时的 Unicode 规范化，只做全角 ASCII 转半角、全角空格转空格、英文字母转小写，服务端与 App 离线版逐码点一致。
**需求**（复核）: 无法比较时一律拒绝（理由 uncomparable）：提案缺少约束中的键、取值不是数值、约束为数值而提案是字典等。约束本身在契约层校验：上限与下限的取值只能是数值或"键 → 数值"。
**需求**（处方闸门）: 三层把关：Skill 产出计划字段就必须是处方类；Agent 运行时，提案字段必须在该 Skill 声明的产出之内，非处方类 Skill 不能产出提案；第一版计划链路在分层不可给计划或未知时不运行训练规划师、营养师、动作教练，计划为空。
**需求**（出错隔离）: 单个 Skill 运行出错时，该 Skill 的输出降级为"本次无意见"（原因 skill_error 与异常类型），不影响其他 Skill；严格模式（测试用）下照常抛出。第一版计划链路对画像中筛查字段逐项校验，不合规的视为未知（于是会被追问），画像必须是 JSON 数据。

### 33. 冲刺 2 复核后的修正（急症误报与漏判、有氧上限）

经过五轮复核与一次再复核，最终规则如下。各轮的重点：
- 第一轮：修误报。
- 第二轮：补回收窄带来的漏判。
- 第三轮：去掉单字背景词，缩小"以前发生过"的作用范围。
- 第四轮：加了条目范围、同分句排除，补直白说法。
- 第五轮：排除条件只用于修饰词与歧义说法。
- 再复核：用连续 3 个分句的窗口，把背景状况与其余症状分开处理，并按病史排除。

**需求**（结构）:
- 判定条目分两类：
  - 背景状况（怀孕、糖尿病、高温、过敏原、哮喘、受伤、催吐）在整句任何位置出现即可。
  - 其余症状须在连续 3 个分句以内同时出现。例如"头疼，是突然开始的，疼得从来没这么厉害"成立；"上个月骑车摔到头了，已经好了，今天吃坏东西吐了"不成立。
- 突发胸痛须在同一分句（within: clause）。
- 症状可以写三种排除：
  - not_preceded_by：前面紧挨着这些字时，这一处不算。
  - not_in_clause_with：分句里有这些字样时，这个症状在该分句不算。
  - still_if_clause_has：分句里同时有这些字样时，not_in_clause_with 不起作用。
- 分句排除用于训练说法、运动出汗、"差点"、感冒、听不清、"想起"、体重。
- 病史也用分句排除，这时允许例外：
  - 心梗、中风、心律不齐、荨麻疹的分句里有"年前、那年、得了、之后、支架、家族、体检查出、上周"等病史字样时不算；
  - 同一分句里有"突然、刚才、正在、又"时照常算，例如"几分钟之前我爸突然中风了"。
- 头部受伤的分句里有"上个月、小时候"时不算；关节肿的分句里有"半年、老毛病"时不算。
- 冷汗与"叫不醒"不受训练说法排除。
- 哮喘须说到发作（"犯了、发作、喘不上"），才判为红旗。
- 受伤后不敢动、动不了，判为红旗。

**需求**（直白说法）:
- "中风、脑梗、脑出血"为急症，"心梗、心脏病发作、没有呼吸、没心跳"也为急症。说的是病史、预防或风险时不算，判法是：
  - 前面紧挨着"以前、之前、曾经、得过"；
  - 或后接"后、过、康复、患者、支架"；
  - 或分句里有"去年、预防、风险、病史"。

  "几分钟之前我爸突然中风了"照常判为急症。
- "叫不醒、喊不醒、叫不应"单独为急症。"叫不醒我"不算，分句里有"闹钟、每天、赖床"也不算。"起床"不排除："早上起床发现我爸叫不醒"必须判为急症。
- "想不开""从楼上跳下去"为红旗（心理危机）。
- "持续"须带"分钟、小时、不断"。
- "做到快晕过去、差点晕倒"为红旗（眼前发黑），不算晕倒；"跑得太快晕倒了"照常判为急症。
- 突然疼得不能负重为红旗。

**需求**（晕倒）: 明确的说法单独命中（晕倒半小时、晕了过去、倒地、一头栽倒、地上一动不动、人没意识了、他失去知觉）。"突然倒了、跑着跑着倒了、眼前一黑……倒"也命中，但后接"杯、水、胃口、半、油"等时不算；这条排除只对"倒了"这类说法起作用。"叫 / 喊 / 拍……没反应、不答应、不应、不醒"须与"倒了、倒下、晕倒、摔倒、躺在地上"等成词说法同时出现才为急症，不用"倒、晕、摔、突然"单字。以下不判为晕倒："他不应该这么练""我给她倒了杯水""突然倒了胃口""我叫了外卖半天没反应，倒是快递先到了""早上闹钟叫不醒我，昨晚喝晕了""叫他别摔杠铃他没反应""我妈每天早上都喊不醒我""练完腿直接倒在地上起不来""滑了一跤栽倒了"。
**需求**（卒中）: 说话不清只用紧挨着的说法，并补充"说话突然不清""说话有点含糊""话都说不清""舌头不灵活"；"含糊其辞""不清不楚"不算。脸歪的判法：只认"嘴歪、嘴角歪、嘴有点歪"、"左边脸 / 半边脸……歪 / 下垂"、紧挨着的"突然脸歪"、"嘴角往一边歪"。不用"左脸、右脸"（"自拍左脸歪了""右脸下垂要做提拉"不算），"突然发现照片里脸歪了"不算。侧别组合不含"歪"，所以"深蹲时身体往右边歪"不算。后接"笑、着笑、歪歪、歪的"不算，前面带"天生"也不算。
**需求**（呼吸）: "快憋死""窒息"须与喘不上气同时出现才为急症；紧挨着的"突然喘不上气、突然呼吸不上来"为急症（"突然加大强度，喘不过气"不算）。休息或轻微活动时喘不上气为红旗，判法是"坐着也、躺着都、平躺、躺下就、不动也、沙发上、走几步"与喘不上气在同一分句，或说"坐着都喘、动不动就喘"、夜里憋醒、什么都没做也喘。"跑完坐着喘了半天""组间休息的时候喘得厉害""冲刺完喘不上气，走两步就缓过来了""以前爬一层楼都喘不上气"不算。
**需求**（过敏）: 全身风团、全身痒、嘴唇肿为红旗；同一分句里提到花生、虾、海鲜、蜜蜂、蛰、过敏等且脸或眼睛肿为红旗；脸或眼睛肿伴痒、起疹子为红旗；脸或眼睛肿、过敏原、喘不上气同时出现为急症。"吃咸了脸肿""哭了眼皮肿""喝了蜂蜜水，早上起来脸肿""吃咸了脸肿，跑步喘不上气""跑步时身上痒"不算。
**需求**（以前发生过）: 说法后接"过"表示以前发生过，这一处不算。以下两种情况例外，照常算：
1. 本分句或后面的分句有具体的复发说法，如"又疼""又发作""也疼""就在刚才"；但后面那个分句说的是别的部位时不算（"以前晕倒过，最近腿也疼"）。单用"又、再次、又犯"不算，比如"现在又胖回来了""想再次挑战马拉松""又犯懒"。
2. 本分句或前一个分句有近期或反复的字样，如"今天、刚才、这周、好几次、每次"；但本分句有"以前、去年、上周、曾经"等久远的时间、又没有近期字样时不算。后面分句里的近期字样不算（"晕倒过一次，最近想开始减肥"）。

例句：
- "去年晕倒过一次，最近想开始减肥" → 不算
- "我晕倒过，今天想问问能不能跑步" → 不算
- "今天跑步之前胸口疼过一阵" → 红旗
- "今天跑步的时候，晕倒过一次" → 急症
- "跑步时胸口疼过好几次" → 红旗
**需求**（统一文字）: 半角句号 ｡ 与小号标点 ﹐﹒﹔﹖﹗ 转成常用写法；上标数字等其余字符不转。服务端与 App 离线版的分句结果逐句一致。
**需求**（有氧上限）: 第一版每周有氧不超过目标值（规则表，300 分钟，ACSM 减重立场每周 200–300 分钟），当前已超过的按目标值给。参数须满足 0 < 保守起点 ≤ 起点 ≤ 目标 ≤ 600，否则启动失败。
**约束**（已知取舍，测试中固定）:
- 宁可多拦：
  - "跑步机突然停了，我头疼得厉害"会判为急症：突发剧烈头痛的范围是相邻分句，否则会漏掉"头疼得像要裂开一样，突然开始的"。单独头疼得厉害本来就是红旗。
  - "我不想活得这么累"会判为红旗：轻生说法宁可多关心一次。
  - "看到有人晕倒了，好吓人"会判为急症：旁人发生的急症也给出呼叫急救的指引（是否暂停本人计划另由问答链路判断）。
  - "心跳很快，看到喜欢的人就头晕"会判为急症。
  - "早上叫我儿子起床，怎么叫都叫不醒"会判为急症：叫不醒单独为急症，宁可多拦。
  - "跑完400米喘不上气，快憋死了"会判为急症：与真实呼救的说法相同。
  - "胸口、手臂的肌肉都有点紧"会判为红旗：顿号不分句，否则会漏掉"胸口、左胳膊都疼"。
  - "我今天想问以前胸口疼过能不能练"会判为红旗：同一分句里既有近期字样又有久远时间，拿不准时按出现处理。
- 缺少上下文的不拦："喊他名字也不应""她跑完步晕了""喘不上气，要死了"会判为无。
**非目标**: 上标数字写的血压；按语义理解句子（词表只做文字匹配，问答链路的意图识别另行处理）。

### 34. 产品定位与离线版暂停（2026-10-21，项目负责人决定）
