## [2026-10-20]

**当日变更概览**: 新增业务模块依赖方向约束：模块按层次只能向下依赖；安全规则模块不依赖任何其他业务模块；违反时项目的标准检查失败。新增工程基础：统一且可替换的时间来源、可复现的标识生成、环境变量配置、不含健康数据原文的结构化日志。新增数据契约（上）：统一的记录结构与首批记录类型、显式的"未知"缺失值、带精度与可信范围的指标结果，契约可导出为 JSON Schema；澄清可选测量项省略即为"未知（没记录）"；新增"围度"记录类型。新增数据契约（下）：Agent 角色与输出类型、计划字段唯一归属（越权即拒绝）、带调整三件套的提案、只读快照、计划版本、模型调用记录。新增数据存储：本地数据库、按编号的迁移、只追加的记录仓储与中文全文检索。新增规则表：可读的规则文件、启动时严格校验、按编号取规则与参数，首个规则集为数据质量。新增测试骨架：红旗正反例、对抗题库、数据驱动的黄金用例，未实现的功能标预期失败。新增模型选型评测：50 道题、可配置的模型列表、自动初筛判分与对比表；评测支持多币种价格、截断判失败与按账户限额限速。新增快进模拟：5 类模拟用户、隐藏真值与陷阱、按天生成 8 周记录并写入记录仓储。独立审查后补充多项澄清：彻底只读、日志取值受限、拒绝覆盖与未来时间、独立连接、严格的文件与数值格式、陷阱校验，并收紧数据存储的可用范围。新增记录提交接口：校验、幂等去重、冲突识别、不回显内容的错误、每请求独立连接、启动时自动迁移。新增批量与离线补交：逐条独立处理与返回、同批内更正排在原记录之后、提交顺序不影响最终结果。新增异常值“待确认”判定：阈值取自规则表、按数据流逐次比较、更正即确认。新增体重趋势：线性回归、标准误与按 t 分布的可信范围，参数取自规则表。新增每日精力选择：5 级精力、当天训练量按规则表只降不升、未选择时不给训练调整。新增完成度、新鲜度与“未知”不计入平均，补上按当地日期的单日热量汇总。第 3 周复盘后：统一的有效记录层、全局规则清单、多项可靠性修复。新增精度判定（体重、训练）：按近 4 周实际记录自动判定 P0–P3。新增精度判定（饮食、恢复）；恢复领域在设备接入前最高 P1。新增判断窗口：按要求的确定程度算出需要多少天、还差什么，超过上限为数据不足。新增指标接口：体重趋势与近 7 天日均热量，带精度、可信范围、状态与还差什么。

### 1. 工程约束：模块依赖方向

**需求**: 业务模块按层次组织（从上到下大致为：对外接口 → 编排与审查 → 各专业 Agent → Skill → 计算 / 指标 / 安全规则 → 共享契约与基础设施），只允许上层依赖下层，禁止下层反向依赖上层。
**需求**: 安全规则模块（急症拦截、人群分层等）除共享契约与基础设施外，不得依赖任何其他业务模块，保证在离线或模型不可用时仍能独立运行。
**需求**: 数据存储只能被编排、审查和对外接口这几层直接使用；Agent、Skill 和计算层不得直接读写存储，只能使用上层传入的数据。
**需求**: 任何违反上述规则的依赖都使项目的标准检查失败（本地提交前检查与持续集成两处一致），失败信息指明违规的调用方与被调用方。
**约束**: 每个业务模块都必须在分层规则中有明确位置；新增模块未登记分层时同样检查失败，避免绕过约束。
**非目标**: 不限制对第三方库的依赖；不检查测试代码的依赖方向。

**澄清**（独立审查后收紧）: 数据存储只能被编排层与对外接口直接使用；调度、记忆等模块需要持久化时，通过契约中定义的数据访问接口，由上层注入实现。

### 2. 工程基础：时间、标识、配置与日志

**需求**: 系统内所有"当前时间"都取自同一个可替换的时间来源；测试与快进模拟可以把时间固定在某一时刻，或向前拨动。
**约束**: 时间一律带时区，统一按 UTC 表示与比较；不带时区的时间在进入系统时被拒绝（报错，不做猜测）。

**需求**: 服务端生成的标识全局唯一；测试与模拟可指定种子，使同一流程两次运行得到完全相同的标识序列。

**需求**: 运行配置通过 `IRONM_` 前缀的环境变量提供，当前配置项：`IRONM_ENV`（`dev` / `test` / `prod`，默认 `dev`）、`IRONM_LOG_LEVEL`（`debug` / `info` / `warning` / `error`，默认 `info`）。
**约束**: 出现未知的 `IRONM_` 变量或取值非法时，启动直接失败，错误信息指明是哪个变量；不静默忽略、不回退到默认值。

**需求**: 日志为结构化格式，每行一条记录，包含时间、级别、来源、事件名和附加字段；日志时间取自上述同一时间来源。
**约束**: 日志不得包含健康数据原文：事件名必须是固定的标识性名称而非自由文本；附加字段只允许标识类（各种 ID）和运行类信息（状态、耗时、计数、错误类型等），写入其他字段时直接报错；记录异常时只记异常类型，不记异常消息内容。

**需求**: 在固定时间和固定种子下，同一流程两次运行产生的标识与日志逐字一致。
**非目标**: 用户本地时区换算（随记录与复盘功能定义）；日志中对数据内容做哈希（首次需要时再定方案）；日志落盘与轮转。

**澄清**（独立审查后补充）: 日志附加字段的取值也受限：标识类与状态类取值只能是不含空格与中文的短标识，路径不得带查询参数；不经结构化接口、直接写入的日志只输出"拒绝了一条不合规日志"及其来源，不输出其内容。配置项名必须全大写，大小写不同的同名配置视为未知配置而失败。
**澄清**（复核后补充）: 取值格式校验只能挡住含中文、空格、查询参数的文字，挡不住英文单词（如 `chest_pain`）；标识类字段只应传入系统生成的标识，这一点靠代码审阅保证。

### 3. 数据契约：记录、缺失值与指标结果

**需求**: 所有记录使用统一结构：记录标识（由客户端生成，用于去重）、用户、记录类型、发生时间、记录时间、来源（用户 / 设备 / 估算）、是否已确认、原文（用户原话或设备原始字段，可空）、规整后的内容；可选附带客户端提示的精度等级。
**需求**: 首批记录类型：训练打卡、按组记录、称重、每周签到、饮食、身体不适、基线测试。每种类型的规整内容字段固定，单位统一（千克、千卡、克）；内容与类型不匹配时拒绝。
**需求**: 记录只追加不修改；改错是追加一条同类型的更正记录，指向被更正的记录。
**约束**: 发生时间不得晚于记录时间；时间必须带时区；来源为设备时必须注明数据流（不同设备的数据不混算）；数值超出物理上可能的范围时拒绝（如体重不在 20–400 千克）；出现未定义的字段、非有限数字（NaN、无穷）或以文本形式给出的数字时拒绝。这些都在入口直接报错，不做纠正或猜测。

**需求**: 缺失值必须显式标为"未知"并注明原因（没记录 / 不愿提供 / 无法解析 / 数据不足），禁止用 0 或空值代替。
**约束**: "未知"不能参与算术运算，也不能当真假值判断，误用时直接报错。

**需求**: 指标结果包含：指标名、所属领域（训练 / 体重与体成分 / 饮食 / 恢复）、数值或"未知"、单位、可信范围（下限、上限、置信水平）、精度等级（P0–P3）、使用的记录条数、窗口天数、状态（正常 / 数据不足 / 已过期 / 待确认）、还差什么、最近一条记录的时间、计算时间、所用公式编号。
**约束**: 字段之间必须一致，否则拒绝：状态为正常时必须有数值；数值为"未知"时不得有可信范围，状态也不能是正常；可信范围的下限不大于上限且包含数值；状态为数据不足时必须说明还差什么。

**需求**: 全部契约可导出为 JSON Schema 文件并纳入版本库；契约改动后未重新导出时，标准检查失败。
**非目标**: 快照、Agent 输出、计划版本、字段归属、模型调用记录（下一步）；异常值"待确认"的具体判定（随记录接口实现）；记录的存储与去重实现。

**澄清**: 可选的测量项（如饮食的热量、蛋白质，按组记录的 RIR / RPE）省略不填时，视为"未知（没记录）"；显式给空值仍然拒绝。

**需求**: 新增记录类型"围度"：必须包含腰围（厘米），可选记录其他部位；数值超出物理上可能的范围时拒绝。
**非目标**: 每 2 周量一次的提醒频率属于提醒与复盘功能，不在本条范围。

**澄清**（独立审查后补充）: 数值与布尔值不视为相等（1 不等于"是"）。

### 4. 数据契约：Agent 输出、字段归属、快照、计划版本与模型调用

**需求**: 首期 10 个 Agent（评估师、安全官、数据分析师、恢复师、训练规划师、动作教练、营养师、行为教练、证据审查官、质量评审官）各有固定角色，只能产出角色允许的输出类型：约束（评估师、安全官、数据分析师、恢复师）、提案（训练规划师、动作教练、营养师、行为教练）、判定（安全官、证据审查官、质量评审官）；任何 Agent 都可以给出"无意见"。
**需求**: 计划中的每个字段有且只有一个负责的提案型 Agent；Agent 提出修改不归自己负责的字段时，在契约层直接拒绝（越权）。同一份输出中不得对同一字段提出两次修改。
**需求**: 每条提案必须写明：字段、原值（首次设定时为空）、新值、依据的事实、触发的规则编号、调整三件套（预期效果、回退条件、复核日期）、引用的依据编号；三件套缺任一项即拒绝；新值与原值相同不算提案。
**需求**: 约束写明作用的计划字段、方向（上限 / 下限 / 排除）、取值、规则编号与理由代码。判定针对某条提案，结果为放行 / 拒绝 / 警告，拒绝和警告必须带理由代码。
**需求**: 快照只读，包含：用户、截至时间、人群分层（A / A′ / B / 协作 / C / D / 暂停）、四个领域各自的精度等级、档案、指标结果、当前计划版本、已生效的约束、上一轮的判定结果。四个领域的精度缺一不可；同名指标不得重复。
**需求**: 计划版本只增不改，包含：版本号、上一版本号、全部字段的取值、与上一版的差异、所用规则表版本与 Skill 版本、创建时间。第 1 版没有上一版本；之后每版的上一版本号必须小于当前版本号；差异里列出的新值必须与本版字段取值一致。
**需求**: 每次大模型调用都留下记录：调用编号、所属请求编号、环节、模型提供方与模型名、提示模板及版本、开始时间、耗时、输入输出用量（可为"未知"）、结果（成功 / 超时 / 出错 / 被校验拒绝）、是否改用模板兜底、出错时的错误类型；记录中不含提示与回答的原文。
**需求**: 新增的契约同样导出为 JSON Schema 并纳入版本库。
**非目标**: Skill 清单、依据卡、决策日志的契约（随 Skill 加载器、依据卡、决策日志任务定义）；计划各字段取值的具体结构（随计划生成定义）；整合器的约束检查、跨字段一致性与"每次最多改 2 项"（随整合器实现）。

**澄清**（独立审查后补充）: "只读"是彻底的：快照、计划版本、提案与约束中嵌套的列表和对象同样不能修改。比较新旧值时数值与布尔值不视为相等。
**澄清**（复核后补充）: 从只读快照或计划版本中取出的值可以直接用于构造新的提案、约束和计划版本。

### 5. 数据存储：数据库、迁移与记录仓储

**需求**: 数据保存在单个本地数据库文件中，路径由配置项 `IRONM_DB_PATH` 指定（默认 `data/ironm.sqlite`）；读取不阻塞写入。
**需求**: 数据库结构由按编号顺序排列的迁移脚本演进；执行迁移时只执行尚未执行过的脚本，重复执行不产生变化。
**约束**: 已执行过的脚本内容被改动、脚本编号不连续或重复、数据库记录了本地不存在的迁移时，迁移直接失败并指明是哪一个；单个迁移执行出错时整体回滚，数据库保持迁移前的状态。

**需求**: 记录写入后可按记录标识读取，读到的内容与写入时完全一致；可按用户列出记录，并按类型、发生时间范围筛选，结果按发生时间排序；服务端另行记下接收时间（取自统一时间来源）。
**需求**: 同一记录标识重复写入时，内容相同视为同一条，只存一次；内容不同则拒绝（冲突），已存的记录不变。
**约束**: 记录只追加，存储层拒绝修改或删除已有记录；更正记录必须指向同一用户、同一类型、已经存在的记录。

**需求**: 记录的原文与身体不适描述可全文检索，支持中文按子串匹配；只返回该用户自己的记录。
**约束**: 检索词少于 3 个字时直接报错（无法可靠匹配），不返回空结果冒充"没找到"；检索词中的特殊符号按普通文字处理。
**非目标**: 档案、计划版本、调度等其他数据表（随各自任务以新迁移加入）；记录接口与离线批量补交；用户数据的导出与删除。

**澄清**（独立审查后补充）: 存储层在任何写入方式下都拒绝覆盖已有记录（包括"有则替换"式写入）。记录时间晚于服务端接收时间超过 5 分钟（允许的设备时钟误差）时拒绝。每个请求使用独立的数据库连接，连接可在处理同一请求的不同线程间传递；多个连接同时写入时排队等待而不报错。迁移目录不存在、目录中出现不合规的文件名（含扩展名大小写不符）时迁移失败。按类型筛选时类型必须以集合给出。
**澄清**（独立审查后补充）: 检索词中的特殊符号必须按普通文字参与匹配（含引号的原文能被含引号的检索词找到）。
**澄清**（复核后补充）: 同一个连接被两个线程同时使用时直接报错（而不是出现难以理解的事务错误）。只禁止其他模块直接引用数据存储，经由编排层间接使用不受限制。
**澄清**（第 3 周复盘后补充）: 一条记录只能被更正一次；要再改，就更正最新的那条更正（形成更正链），不允许对同一条记录产生两个分叉的更正。

### 6. 规则表：格式、加载与首个规则集

**需求**: 业务阈值与判定规则写在人可直接阅读的规则文件中，不写死在代码里；按规则集分文件，每个规则集有名称与版本。每条规则包含：编号、标题、审定状态（草稿 / 待审定 / 已审定）、来源（指南 / 设计 / 借鉴 / 估算，除"设计"外必须写明出处）、参数（阈值等），可附说明。
**约束**: 规则编号在全部规则集中唯一；规则集名称与文件名一致且不重复；规则目录由配置项 `IRONM_RULES_DIR` 指定（默认 `rules`）。
**需求**: 启动时加载全部规则表；任何格式问题都使启动失败，错误信息指明文件（及规则编号）：缺少字段、来源不全、编号重复、未定义的字段、同一层级出现重复的键、文件扩展名不规范、目录里没有任何规则表、内容无法按纯文本数据解析（如未加引号的日期）。
**需求**: 程序按编号取规则，编号不存在时报错；取参数时按使用方声明的类型校验，不符时报错并指明规则编号。能列出各规则集的版本，供计划版本记录"用了哪一版规则"。
**需求**: 规则文件的格式导出为 JSON Schema，供编辑规则时校验。
**需求**: 首个规则集"数据质量"，状态均为待审定：
- 体重在 7 天内变化超过 2 千克，标"待确认"【设计】；
- 单日热量低于 500 或高于 6000 千卡，标"待确认"【设计】；
- 超过 10 天没有新的称重，体重类指标标"已过期"【设计】；
- 饮食调整的最低数据量：每 7 天至少 4 天有饮食记录、每周至少 1 次称重【借鉴 MacroFactor】。
**非目标**: 各规则的判定执行（随异常值、新鲜度、复盘等功能实现）；规则下线开关；急症词表（由安全模块独立维护，不走规则表，保证安全模块不依赖其他模块）。

**澄清**（独立审查后补充）: 规则目录中除说明文档（.md）与隐藏文件外，任何不是 .yaml 结尾的文件都使加载失败（含 .YAML、.yaml.bak 等）。规则文件中的数字、真假值只按现行标准写法识别：1:30、010、yes / on 等旧式写法一律当文字处理，再由类型校验报错，不会被悄悄换算。
**澄清**（复核后补充）: 按使用方声明的类型取参数时严格校验，文字不会被转换成数字或真假值。

### 8. 模型选型评测

### 9. 快进模拟：模拟用户与 8 周数据

**需求**: 模拟用户用数据文件定义，包含：可见档案（性别、年龄、身高、起始体重）、记录习惯（称重日、训练日、饮食记录方式、签到日）、隐藏真值（分阶段的真实体重变化速度、测量噪声、训练完成概率、疲劳走势）以及陷阱。首批 5 类：按计划执行、完成度低、疲劳累积、每周只称 1 次、习惯模式（饮食不记热量）。
**需求**: 陷阱至少包括：单次体重尖峰、换秤（数据流改变并带固定偏差）、单位写错（把斤当公斤记）、情况变差时停止记录、一段时间完全不记录（依从性缺口）。每个陷阱生成的记录都登记在真值里，供以后检验"有没有被假信号骗、真变化有没有及时发现"。
**需求**: 快进运行器从起始日开始逐天推进统一时间来源，当天的记录在当天写入记录仓储（接收时间即当天的模拟时刻）；每天结束、每周结束时调用登记的回调（供以后接入复盘）。默认生成 8 周。
**约束**: 同一模拟用户、同一种子两次生成的记录逐字一致；每个随机值只由（种子、用户、日期、项目）决定，增减一个陷阱不改变其他天的记录。隐藏真值不出现在任何记录中。生成的记录全部符合记录契约。
**需求**: 提供一条命令跑完 5 类模拟用户 8 周，输出汇总：各类记录条数、陷阱条数、真实与测得体重的首末值。
**非目标**: 复盘决策与判分（随复盘、决策表任务）；模拟用户对系统建议的反应（模拟用户的走势不随建议改变）。

**澄清**（独立审查后补充）: 陷阱的天数必须落在模拟范围内；同一天不能有两个单日陷阱；起止天顺序必须正确，否则模拟用户加载失败。任何概率取值下生成的记录都必须符合契约。汇总中的"测得体重"只剔除尖峰与单位写错这两类假读数，换秤后的读数照常统计。

### 10. 记录提交接口

**需求**: 提供提交一条记录的接口，内容按记录契约校验。首次提交返回"已创建"；同一记录再次提交返回"重复"，库中只存一次；同一记录标识但内容不同返回"冲突"，已存的记录不变。返回结果中带记录标识。
**需求**: 校验失败、记录时间在未来、更正指向不合规的记录时，返回"请求不合法"，并给出出错的字段位置与原因；错误信息中不回显提交的取值（可能含健康数据原文）。
**需求**: 服务启动时自动执行尚未执行的迁移，迁移失败则启动失败；每次请求使用独立的数据库连接；接收时间取自统一时间来源。
**需求**: 每次提交写一条结构化日志，含记录标识、结果与耗时，不含记录内容。
**约束**: 两个请求同时提交同一条记录时，只存一条，一个返回"已创建"、另一个返回"重复"，不出现服务器错误。
**非目标**: 批量与离线补交（下一步）；登录与身份校验（目前以记录中的用户为准，上线前必须由登录身份决定用户）；请求频率限制。
**澄清**（第 3 周复盘后补充）: 校验错误的原因说明中若含有提交的取值（如类型名写成一句话），改为通用说明；请求体超过 2 MB 返回"请求过大"；嵌套过深等无法解析的请求体返回"请求不合法"而非服务器错误。提交的记录必须属于当前用户（登录功能完成前，当前用户由请求头给出），否则拒绝；查询类接口不再从参数中读取用户。
**澄清**（复核后补充）: 校验错误的原因说明一律使用系统自己的措辞（限值取自契约本身），不使用校验库的原文；请求头声明的大小超过上限时，不读取请求体直接拒绝。

### 11. 批量与离线补交

**需求**: 提供一次提交多条记录的接口（离线队列上传用），每批 1–500 条。每条单独校验、单独入库、单独返回结果（已创建 / 重复 / 冲突 / 不合法，并带它在本批中的位置与记录标识）；一条出错不影响同批其他记录。
**需求**: 同一批中，更正记录在它所指向的原记录之后处理，无论它们在批内的先后。离线补交的记录（发生时间、记录时间都早于接收时间很久）照常接受，接收时间为实际上传时刻。
**约束**: 结果与提交顺序无关：同一组记录无论怎样打乱顺序、重复提交、分成多批（更正不早于其原记录所在的批次），最终存下的记录完全相同，按用户列出的结果也完全相同（同一发生时间的记录按记录标识排序，而不是按到达先后）。
**约束**: 空批、超过 500 条、请求体格式不对时整批拒绝；单条的错误信息与单条接口一样不回显提交内容。每条记录各写一行提交日志，另写一行批次日志（条数、耗时）。
**非目标**: 跨批次的"更正先于原记录到达"（客户端离线队列按产生顺序上传，不会出现）；批量提交的整体事务（逐条入库，失败可安全重传）。
**澄清**（第 3 周复盘后补充）: 同一批中同一记录标识出现内容不同的多条时，这些条全部判为冲突、都不入库（与库中已有内容相同的那条判为重复），结果与它们在批内的先后无关。
**澄清**（复核后补充）: 同一批中有多条不同的更正指向同一记录时，这些更正一律判为不合法（已在库中且内容相同的判为重复），结果与先后无关。

### 12. 异常值"待确认"

**需求**: 体重在规定天数内（含）的变化超过规定幅度时，这次称重标为"待确认"；单日热量低于下限或高于上限时，该日标为"待确认"。阈值一律取自规则表（数据质量规则集），判定结果带触发的规则编号。
**需求**: 对一位用户的全部称重按发生时间逐次判定：每次称重与"近期水平"比较，即同一数据流中、规定天数内最近至多 3 次未被标为"待确认"的有效读数的中位数；规定天数内没有可比读数时不标。不同数据流（如换了秤）之间不比较。
**约束**: 不与单一的上一次读数比较：上一次读数本身带测量噪声时，尖峰会漏判，而漏判的尖峰又会让其后的正常读数被误标（快进模拟中"按计划执行"用户的尖峰陷阱即暴露了这一问题）。
**需求**: "待确认"不修改记录本身。用户确认或修正一条读数的方式，是追加一条指向它的更正记录：被更正的记录不再是有效读数，更正记录视为用户已确认，不会被标为"待确认"。
**澄清**: 记录中的"已确认"只表示估算值（如从一句话抽取的饮食）已经用户确认，与异常值是否复核无关。
**非目标**: 单日热量的汇总（需先定用户所在时区，随完成度与新鲜度任务）；"待确认"的提醒与界面。
**澄清**（第 3 周复盘后补充）: 若比较基准只有一条读数（没有其他读数印证），而其后连续若干次读数（规则表，现为 2 次）彼此一致、又与当前读数一致，则判定基准那条有误：改为标记它，并以新读数为准，不再把其后的正常读数都标为"待确认"。判定结果随新数据而变，不写回记录。近期水平取的读数次数取自规则表。用户的确认（更正）记录沿用被更正读数的数据流。
**澄清**（复核后补充）: 推翻基准需同时满足：其后的读数都与当前读数一致（相差不超过规则表中的容差，现为 1 千克），且都与基准相差超过跳变幅度。只满足其一时不推翻（例如尖峰之后回到正常水平的读数，与基准一致而与尖峰不一致）。

### 13. 体重趋势与可信范围

**需求**: 对给定时间窗口内的体重读数做线性回归，给出：读数条数、覆盖天数、每周变化（千克 / 周）、标准误、按规定置信水平的可信范围（用 t 分布，读数少时范围相应变宽）、残差标准差。
**需求**: 参与计算的读数：有效（未被更正取代）、未被标为"待确认"、与最近一次读数同一数据流（不同的秤不混算），且落在窗口内。
**需求**: 置信水平与最少读数条数取自规则表；读数不足或所有读数在同一时刻时，结果为"数据不足"，并说明还差几次称重，不给出趋势数值。
**约束**: 计算结果与手算样例一致；t 分布分位数与统计表一致（至少 3 位小数）。
**非目标**: 精度等级与判断窗口的确定（随精度判定、判断窗口任务）；指标结果的组装与接口（随指标接口任务）。
**澄清**（第 3 周复盘后补充）: 参与计算的读数覆盖天数少于规则表规定的下限（现为 3 天）时为"数据不足"，并说明还需覆盖的天数。结果统一用状态（正常 / 数据不足）与"还差什么"表示。
**澄清**（复核后补充）: 覆盖天数下限必须大于 0；即便调用方给出 0，所有读数在同一时刻时也判为数据不足，不出现计算错误。

### 14. 每日精力选择与训练量调整

**需求**: 用户每天第一次使用前选择当天精力，共 5 级：1 很差、2 疲惫、3 一般、4 良好、5 充沛。选择作为一条记录保存；同一天可以改选，以当天最后一次选择为准。"一天"按用户所在时区的 0 点到 24 点计算，时区用标准名称（如 Asia/Shanghai）。
**需求**: 当天训练任务量据精力调整，每一级对应的调整方式写在规则表中（初版，待审定）：
- 5 充沛、4 良好：照常（不因精力好而加量）；
- 3 一般：降低难度，组数约 80%，用力程度上限降 1 级；
- 2 疲惫：只留轻松训练，组数约 50%，用力程度上限降 2 级；
- 1 很差：只做最低任务或休息，不安排正式训练组。
调整结果带规则编号，并能换算出某个训练项调整后的组数与用力程度上限。
**约束**: 精力只能让训练量下降，不能让它超过原计划。当天还没有选择精力时，结果为"未选择"，不给出任何调整，也不默认按"照常"处理；当天训练任务必须在用户选择之后才能确定。
**约束**: 精力选择不替代安全判断：精力"很差"时提示用户，如有胸痛、头晕、心慌等不适请走安全通道，而不是只降训练量。
**非目标**: 训练计划本身的生成与"今日"页面（随后续任务）；用户档案中的时区字段（档案功能完成前由调用方给出时区）；把精力纳入恢复、复盘的长期判断。
**澄清**（第 3 周复盘后补充）: 调整后的组数按四舍五入（0.5 进位）取整。查询今日精力时，用户取自当前用户，而非查询参数。

### 15. 完成度、新鲜度与"未知"不计入平均

**需求**: 求平均时只用已知值，"未知"不计入；全部为"未知"时，结果为"未知（数据不足）"，不算作 0。
**需求**: 体重新鲜度：最近一次可信称重（有效、非待确认）距今超过规定天数（规则表，现为 10 天）时为"已过期"，恰好等于规定天数不算过期；从未称重时为"没有数据"，与"已过期"区分。结果带最近称重时间与规则编号。
**需求**: 训练完成度：对照计划的训练日计算，完成、练一半、没练的计分取自规则表（现为 1、0.5、0）；计划日没有打卡记录的记为"未知"，不当作没练，不计入完成度；同时给出有记录的计划日占比。日期按用户所在时区计算；非计划日的训练不计入。
**需求**: 单日热量按用户所在时区的当地日期汇总：当天所有饮食记录都有热量时为其总和；当天任一餐的热量未知，或当天没有饮食记录时，当天总量为"未知"（部分记录会让总量偏低，空白优于部分记录）。只有已知的单日总量参与"待确认"判定。
**约束**: 属性测试：在任意一组数值中任意位置插入任意多个"未知"，平均值不变。
**非目标**: 把这些结果组装成指标结果与接口（随指标接口任务）；饮食调整的最低数据量判断（随复盘任务）。
**澄清**（第 3 周复盘后补充）: 计划训练日为 0 时，记录占比为"未知"。新鲜度结果统一用状态（正常 / 已过期 / 数据不足）表示；从未称重为"数据不足"并说明还差 1 次称重。指标结果中"最近一条记录的时间"缺失时为"未知"而非空值。所有规则参数在服务启动时按使用方声明的类型校验，写错即启动失败。
**澄清**（冲刺 1 末审查后补充）: 单日热量汇总中，未经用户确认的估算视为没有热量（与精度判定一致）。

### 16. 全局规则清单（每个计算都必须满足）

**需求**: 以下规则对每一个读取记录做计算的功能都成立，新增计算功能时逐条核对，并有对应测试：
1. **更正**：只使用有效记录（被更正取代的记录不参与；更正链取最新一版），通过统一的有效记录层取得，不各自实现。
2. **未知**：缺失值用"未知"并注明原因，不用 0 或空值；平均、占比等只对已知值计算，全部未知时结果为"未知"。
3. **时区**：涉及"哪一天"的计算按用户所在时区的当地日期。
4. **截止时间**：只使用发生时间不晚于截止时间（as_of）的记录。
5. **阈值**：阈值与计分取自规则表，结果带规则编号；参数在启动时校验。
6. **顺序无关**：结果不随记录到达或排列的先后改变。
**约束**: 这些规则由公共层实现（有效记录层、只对已知值求平均、当地日期换算），各计算功能调用公共层，不重复实现。

### 17. 精度判定（体重、训练）

**需求**: 按截止时间前 4 周（规则表）的实际记录，分别判定体重与训练两个领域的精度等级 P0–P3，结果带规则编号与判定依据（各周记录天数、各级达标的训练日占比等）。
**需求**: 体重：以用户所在时区的当地日期计算每周称重天数（同一天多次只算一天；被更正取代的不计，"待确认"的读数仍算称过重）。
- P3：4 周内至少 14 天称重，且至少 3 周每周不少于 3 天；
- P2：至少 3 周每周不少于 2 天；
- P1：至少 3 周每周不少于 1 天；
- P0：其他。
**需求**: 训练：以当地日期确定训练日（当天有打卡或按组记录），每个训练日的记录程度为：
- 3：有按组记录，且当天每组都有 RIR 或 RPE；
- 2：有按组记录但缺 RIR / RPE，或打卡时填了用力程度；
- 1：只有打卡状态；
领域精度为最高的等级 L，使"记录程度 ≥ L 的训练日占比"不低于 75%；4 周内训练日少于 4 天时为 P0。
**约束**: 以上周数、天数、比例全部取自规则表（初版，待审定）；遵守全局规则清单（§16）。每一档的边界都有黄金用例。
**非目标**: 饮食与恢复两个领域（下一步）；精度对计算方法与判断窗口的影响（随判断窗口任务）。
**澄清**（冲刺 1 末审查后补充）: 训练日指当天有按组记录，或有状态为"完成""练一半"的打卡；只有"没练"打卡的日子不算训练日。

### 18. 精度判定（饮食、恢复）

**需求**: 饮食：以当地日期确定有饮食记录的日子，每天的记录程度为：
- 3：当天每一餐都有热量与蛋白质，且都是用户自己填写的数值（不是估算）；
- 2：当天每一餐都有热量（可以是经用户确认的估算）；
- 1：其他（有记录但缺热量；未经确认的估算视为没有热量）。
领域精度：4 周内有饮食记录的天数不少于规定天数（现为 16 天）时，取最高的 L（3 或 2）使"程度 ≥ L 的天数占比"不低于 75%；否则，若至少 3 周的每周签到回答了"按计划吃了几天"，为 P1；否则为 P0。记录天数够但占比不到 P2 的，同样按签到判断 P1。
**需求**: 恢复：P3、P2 需要设备的睡眠、心率变异性、静息心率等数据，设备接入前恢复领域最高为 P1。至少 3 周的每周签到填了疲劳或睡眠，或 4 周内至少 16 天选择了每日精力，为 P1；否则为 P0。
**约束**: 天数、周数、比例取自规则表（初版，待审定）；遵守全局规则清单（§16）；每一档的边界都有黄金用例。
**非目标**: 设备数据的接入与恢复领域 P2、P3；精度对计算方法的影响（随判断窗口任务）。
**澄清**（冲刺 1 末审查后补充）: 饮食与恢复的窗口天数必须是 7 的倍数，所需周数不超过窗口内的周数，启动时校验。

### 19. 判断窗口（需要多久、还差什么）

**需求**: 先定"需要多确定"，再算"需要多久"：体重趋势可信范围的半宽不超过规定值（规则表，现为每周 0.25 千克）才能下结论。给定每周称重次数与体重日常波动，算出满足要求的最少天数：假定在窗口内均匀称重，按 §13 同样的回归与 t 分布计算可信范围半宽。
**需求**: 每周称重次数取近 4 周的实际称重天数平均；体重日常波动在可信读数足够（规则表，现为 6 次）时取用户自己回归的残差标准差，否则取规则表中的默认值（现为 0.5 千克），结果注明取自哪里。
**需求**: 所需天数超过上限（规则表，现为 56 天）时为"数据不足"，说明每周至少需要称几次才能在上限内得出结论；所需天数在上限内时，比较已有的数据覆盖天数，够了为"正常"，不够为"数据不足"并说明还差几天；同时给出"每周多称一次可提前约几天"。近 4 周没有称重时为"数据不足"，说明还差称重。
**约束**: 黄金用例覆盖每天称、每周 2 次、每周 1 次三种情况，并附手算过程。方案中"每天称约 2 周"为估计，按本计算为约 3 周（波动 0.5 千克时 21 天）。
**非目标**: 饮食、训练等其他判断的窗口（随复盘决策表任务）；"拒绝后 4 周内不再提示"的提示频率控制（随提醒任务）。
**澄清**（冲刺 1 末审查后补充）: 每周已称 7 次仍无法在上限内达到要求时，不再提示"每周至少称 7 次"，改为提示固定时间称重以减少波动。
**澄清**（冲刺 1 后用户确认）: 每周称重次数按近 4 周平均；若最早一次可信称重距今不足 4 周，按称重间隔估算：（称重天数 − 1）÷ 最早一次距今的天数 × 7；只称过 1 天时按每周 1 次（新用户头几天天天称，不会被当作每周只称一两次；每 7 天称一次也不会因首尾计数被高估）。精度判定仍按固定的 4 周计算。

### 20. 指标接口

**需求**: 提供查询当前用户指标的接口（时区由调用方给出），返回：计算时间、四个领域的精度等级，以及指标结果列表；每个指标结果符合指标契约（数值或"未知"、单位、可信范围、精度、使用的记录条数、窗口天数、状态、还差什么、最近一条记录时间、计算时间、公式编号）。
**需求**: 首批指标：
- 体重趋势（千克 / 周）：窗口取判断窗口所需天数（不足或无法确定时取上限）；有趋势估计时给出数值与可信范围，即使状态为"数据不足"也给出（界面标为暂定）；还差什么取判断窗口的结论。
- 近 7 天日均热量（千卡）：只对已知的单日总量求平均；已知天数少于规则表的最低天数（现为 7 天中 4 天）时为"数据不足"并说明还差几天。
**需求**: 状态按优先级确定：已过期 > 有待确认的读数 > 数据不足 > 正常。
**约束**: 只读取计算所需的最近一段记录，回看天数由规则表中的各窗口推算（不另设数字），历史记录再多也不影响响应；指标组装放在计算层，接口只负责取数与返回。遵守全局规则清单（§16）。
**非目标**: 训练完成度指标（需要计划，随计划任务）；其他领域的更多指标；界面展示。
**澄清**（冲刺 1 演示后补充）: 体重趋势判为"正常"，还要求实际算出的可信范围半宽不超过目标（判断窗口按均匀称重的模型估算所需天数，实际称重不均匀或波动更大时，实际范围可能更宽）；超过时为"数据不足"，还差的天数按"标准误约与天数的 1.5 次方成反比"估算：所需天数 ≈ 当前窗口天数 ×（当前半宽 ÷ 目标）^(2/3)。
**澄清**（冲刺 1 末审查后补充）:
- 已有数据覆盖超过所需天数时，体重趋势的窗口随覆盖天数增长（不超过上限），使"还差 N 天"能够兑现，避免状态来回跳；到上限仍不达标时提示固定时间称重。
- 近 7 天日均热量不含今天（今天尚未结束，部分记录会拉低均值并误报异常）。
- 回看范围内没有称重时，另取范围之外最近的几次称重，用于区分"已过期"与"没有数据"；取数时一并取得指向已取记录的更正（即使更正把发生时间改到范围之外）。
- 时区名不合规（含过长）一律返回"请求不合法"，不出现服务器错误。

### 21. 急症词表与匹配

**需求**: 安全模块对用户的一句话给出判定：急症（立即就医 / 拨打 120）、红旗（暂停相关训练、尽快就医）或不触发，并给出命中的词表条目编号与类别。判定只看词表，不调用模型、知识库或其他业务模块，离线与模型故障时照常工作。
**需求**: 词表是一份人可读的文件，分两层：
- 症状：一组同义说法。任一说法出现即命中；或者写成几组词，同一分句里每组都出现才算命中（如"胸口"与"痛"可以隔开几个字）；血压按数值判断（收缩压或舒张压达到阈值）。
- 判定条目：若干症状在同一句话里都出现时，给出急症或红旗。多个条目命中时取最高一级（急症高于红旗）。
**需求**: 判定只升不降：拿不准时取更高一级。
**约束**: 只用最简单的匹配方式（文字包含、分句内多组同时出现、血压数值），保证前端离线版用同一份词表能得到相同结果。匹配前统一文字：全角转半角、英文转小写、去掉空白；分句按中英文逗号、句号、问号、感叹号、分号、顿号与换行切分。
**约束**: 词表严格校验，服务启动时加载，有误即启动失败：编号唯一；判定条目引用的症状必须存在；每个症状至少被一个条目使用；说法不能为空、不能含分句符号，并且已是统一后的写法。词表带版本与审定状态，初版为待审定，只能由人修改。
**约束**: 判定结果与日志都不含用户原话。
**澄清**: 否定说法、已经缓解、转述他人过去的经历（"没有胸痛""以前晕倒过"）留到 D22 处理；本条只要求红旗测试集的正例全部判对级别，D22 之前这几条反例单独标为预期失败。
**非目标**: 否定句识别与前端离线版（D22）；人群分层（D23）；三档回答与红旗四段式（D24）。

### 22. 否定说法识别与离线版

**需求**: 症状说法紧跟在否定词之后（"没有胸痛""不头晕""未见红"）时，这一处不算出现；同一分句里同一症状还有别处没被否定，仍算出现。组合说法中任一组只在否定处出现，这一组合不算命中（"胸口不疼了"）。
**需求**: 症状说法后紧跟"过"（不是"过去"）表示以前发生过（"上周胸口疼过""以前晕倒过"），这一处不算出现；但整句话里有再次发生的字样（"又""再次""刚才"等）时，以前发生过的也照常算。
**需求**: 否定词、例外（"差点没晕倒"仍算出现）、"过"与再次发生的字样都写在词表里，由人维护。
**需求**: 提供 App 离线版：由同一份词表生成离线数据文件，配一个不依赖任何第三方库的脚本实现同样的判定；词表改动后未重新生成即检查失败。
**约束**: 只升不降：否定只能取消紧挨着的一处说法；拿不准是否否定时按出现处理（假设、担心、提问等说法不做识别）。血压数值不受否定影响。
**约束**: 离线版与服务端对同一句话的判定（级别、条目编号、类别）完全一致：红旗测试集、改写说法、日常说法与大量随机拼接的句子全部比对。
**非目标**: 假设与提问（"万一晕倒怎么办"）的识别；人群分层（D23）；回答模板（D24）；App 页面本身（D41 起）。
**澄清**（用户确认）: 前端做手机 App，不做 PWA 网页；技术栈为 React Native + Expo（TypeScript），一套代码出 iPhone 与安卓。离线判定脚本即为 App 代码的一部分（app/src/safety/），用 Node 直接运行做一致性检查。

### 23. 人群分层与实时重新分层

**需求**: 安全模块根据用户的筛查信息给出安全分层，并列出依据。筛查信息包括：出生日期、性别、身高、最近体重、最近腰围、已申报的健康状况（问卷）、红旗记录与就医确认；每项都可以是"未知"。
**需求**: 分层（第一期只有减脂场景）：
- 暂停：有红旗或急症记录，且之后没有"已就医、可以运动"的确认。
- D 暂不开放：未满 18 岁。
- C 记录与协作：孕期、哺乳期、产后 1 年内、心脏病、肾脏病、正在用药的糖尿病、伤后康复中、进食障碍史、进食障碍信号、未在医生指导下使用减重药物。
- 不适用（减脂）：BMI 低于 18.5。
- 协作：在医生指导下使用减重药物。
- B 保守：65 岁及以上、高血压、近期受伤、BMI 达到 32.5。
- A 完整：BMI 达到 24，或腰围达到中心型肥胖前期（男 85 厘米、女 80 厘米）。
- A′ 体态减脂：BMI 18.5–23.9 且腰围未达上述值。
**需求**: 同时满足多层时，主层按上面的顺序取最靠前的一层；其余满足的层一并列出（供热量等计算取更保守的约束，如 65 岁、BMI 22 的用户主层为 B，同时满足 A′）。
**需求**: 信息不全时：决定主层所需的信息缺失则给不出分层（"未知"），并列出还差什么；只缺腰围或性别、且 BMI 在 18.5–23.9 时，按 A′ 保守假设，并标明是假设、还差腰围。决定主层用不到的信息缺失不影响结果（如已在暂停或 C 层）。
**需求**: 实时重新分层：聊天中的一句话被判为红旗或急症时，立即记一条红旗记录，分层当场变为暂停；命中进食障碍类条目的，同时记为进食障碍信号，就医确认后仍在 C 层。给出新旧分层相比是更严、更松还是不变。
**约束**: 年龄按用户所在时区、截至计算时间的当地日期计算（生日当天算满岁）；截至时间之后的红旗与就医确认不计入。BMI 按一位小数四舍五入后与界值比较。年龄、BMI、腰围界值与各层对应的健康状况写在规则表（待医学顾问审定），服务启动时校验；分层顺序写在代码里。安全模块不依赖规则模块，只通过共享契约读取规则参数。
**约束**: 结果带规则编号；每层边界都有黄金用例（17/18 岁、64/65 岁、BMI 18.4/18.5、23.9/24.0、32.4/32.5、男女腰围界值）。
**非目标**: 从聊天中识别新诊断（"我怀孕了"）并更新问卷（随意图识别）；档案与问卷的存储和接口（随建档）；各层的具体服务限制（热量见 D25，处方类 Skill 见 D27）；其他场景包的分层。

### 24. 三档输出、红旗四段式与四项拒答

**需求**: 安全模块对一句话结合当前分层给出安全决定：输出档位（完整 / 保守 / 暂停并转介）、是否允许给出训练或饮食计划、需要告知用户的提示、命中的拒答类型，以及由模板生成的回答段落。对应关系：
- 这句话判为急症或红旗，或分层为暂停 → 暂停并转介，不给计划。
- A、A′ → 完整，可给计划。
- B、协作 → 保守，可给计划，并提示已按保守规则安排（协作层另提示药物问题请问医生）。
- C、不适用（减脂）、D → 保守，不给计划，并分别提示：只提供记录与专业沟通摘要 / 不提供减脂计划 / 未满 18 岁暂不开放。
- 分层未知 → 保守，不给计划，提示需要先补充哪些信息。
**需求**: 红旗回答四段式：安全结论 → 需立即停止的活动 → 不能判断的部分 → 建议的专业帮助（急诊或科室，以及就诊时可以告诉医生的信息）。急症的结论与专业帮助都写明拨打 120；红旗写明尽快到哪个科室就诊，以及就医确认后如何恢复训练建议。停止的活动、科室与可带的信息按命中条目的类别给出，多个类别合并去重。
**需求**: 四项拒答：不诊断（含解读检查报告）、不开处方（含用药、剂量、联合用药、推荐药品）、不制定治疗方案、不提供紧急医疗服务（不能代为呼叫急救）。识别使用单独的拒答词表，匹配方式与急症词表相同（同义说法、分句内多组同时出现、紧挨着的否定词）。提到药名但没有问用法用量（"我在吃二甲双胍，能做力量训练吗"）不算。每种拒答有固定的回答段落，药物一律转医生或药师。
**需求**: 回答的文字（段落标题、四段式各段、各类别的停止活动与科室、拒答与提示）写在一份人可读的模板文件中，由人维护；回答中不出现用户原话。四段式模板随离线词表一起导出，App 离线版生成与服务端相同的四段式。
**约束**: 模板与拒答词表严格校验、服务启动时加载：急症词表中出现的每个类别都要有对应的模板；每种拒答、每个提示都要有文字；占位符只能是规定的几个。
**约束**: 对抗题库中能由规则确定判断的题（运动中胸痛、违禁药物、减重药物剂量、开处方与治疗、诱导诊断、泻药用量）必须全部给出正确的档位或拒答类型；其余题依赖问答功能（D44 起）。
**非目标**: 由模型生成的正文与回答评分（随问答）；"疼痛类回答必须写明就医条件"的检查（随问答）；保守档具体规避了哪些动作（随训练规划）。

### 25. 热量计算

**需求**: 根据筛查信息（性别、出生日期、身高、最近体重）、用户选择的身体活动水平与分层结果，计算每日热量目标，全部标为"估算"，并写明用到的规则编号：
- 静息能量消耗（Mifflin-St Jeor）：男 = 10 × 体重（千克）+ 6.25 × 身高（厘米）− 5 × 年龄 + 5；女 = 同式 − 161。
- 每日总消耗 = 静息能量消耗 × 身体活动水平。活动水平三档，取 FAO/WHO/UNU 各档区间的中间值：久坐或轻度 1.55、中度 1.85、重度 2.20。
- 能量缺口按分层：A 500、A′ 300、B 500、协作 300 千卡；同时满足多层时取其中最小的缺口。其余分层（暂停、D、C、不适用）不给热量目标。
- 热量目标 = 每日总消耗 − 缺口，但不低于底线（女 1200、男 1500 千卡，任何情况不低于 800）；被底线抬高时写明，实际缺口随之变小，底线高于每日总消耗时实际缺口为 0、不给负缺口，并提示靠增加活动。
- 营养素：碳水 / 脂肪 / 蛋白质按热量占比 55 / 25 / 20，可选高蛋白 50 / 25 / 25；克数按每克 4 / 9 / 4 千卡换算。三餐按 30 / 40 / 30 分配。
**约束**: 系数、活动水平、缺口、底线、占比全部写在规则表（初版待审定），服务启动时校验（占比之和为 100、底线不低于绝对底线等）。年龄按用户时区的当地日期。先算出不取整的结果，最后把热量四舍五入到整千卡；营养素克数与三餐热量由取整后的目标换算并四舍五入，最后一餐取差额，保证三餐之和等于目标。
**约束**: 信息不全（性别、出生日期、身高、体重或活动水平未知）时给不出目标，列出还差什么；分层不允许给计划时给不出目标并写明原因，不用 0 代替。可给计划的分层与三档输出中"可给计划"的分层一致。
**非目标**: 减重速度目标与阶段复盘（随复盘）；精确型的能量平衡校正（反推个人消耗）；简化型与习惯型饮食模式的表达；接口与界面。

### 26. 规则、词表与模板的审定（Claude 版本）

**需求**: 项目负责人委托 Claude 对照公开资料逐项审定所有"待审定"的规则表、急症词表、拒答词表与回答模板。每一项写明结论（维持 / 修改）、改了什么、依据（附链接）与证据强弱，记在 `spec/review_log.md`；审定完成的标为"已审定"，文件中注明由 Claude 代为审定、未经执业医师或注册营养师复核。暂不能落地的修改记为后续任务并写明在哪一天做。
**需求**（数据与指标）:
- 体重趋势：同一当地日期多次称重只取当天第一次可信读数参与回归（与精度、判断窗口按"称重天数"计一致）；至少覆盖 7 天；考虑相邻读数波动的相关性，标准误乘以 √((1+r)/(1−r))，r = 相关系数 0.4 的"平均间隔天数"次方（判断窗口的天数估算同样计入）。
- 趋势窗口：在"所需天数"到"已覆盖天数"（不超过上限）之间，取可信范围达到要求的最短窗口，使结论尽量反映近期；都达不到时取其中最长的，并说明还差什么。
- 跳变"待确认"：阈值为 2 千克与近期水平 2.5% 中较大者；可比读数的时间窗为 8 天（容下"每周同一天、晚一点称"）。超过 7 天仍未确认的读数仍不参与计算、仍列为待办，但不再决定体重趋势的状态。
- 近 7 天日均热量：已知天数中至少 1 天是周五、周六或周日，否则为数据不足（周末摄入通常更高）；删除未被使用的"最少称重次数"参数。
- 训练完成度：有记录的计划日占比低于 75% 时为数据不足（与训练精度一致），仍给出已记录日的完成度。
**约束**: 新参数全部写在规则表并启动时校验；修改后对应的黄金用例与测试同步更新，快进模拟 5 类用户的可信范围仍覆盖真实趋势。
**非目标**（后续任务）: 饮食目标变更后趋势窗口从变更日重新开始（需要饮食目标记录，随复盘决策）；用"摄入 − 体重变化"反推个人消耗时摄入窗口与趋势窗口一致（随精确型能量校正）。
